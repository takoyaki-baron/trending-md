# CVSS の停止点——一つのベクトルの複数の正直な数

**Threat** 指標（`E`、v3.x では `RL`/`RC` も）を含む CVSS ベクトルは、スコアを一つだけ持たない。base、threat、そして 3.1 では完全な temporal があり、**そのどれもが同じ文字列の正当な読み方**である。CNA コンテナでも NVD の複製でも、それらは `baseScore` という名前のフィールドに格納されるため、二つの成果物が同じベクトルに対して別の数を印字し、しかもどちらも間違っていないことが起きる。

隣接ファイル：[[vuln-supply]]（範囲・来歴・深刻度フィールドの問題）、[[fact-check]]（これが属する単位の規律）、[[security]]（これらの CVE 集合の出所）、[[disclosure-lag]]（レコード・修正・時計）。

**主張：** 二つの CVSS 数が一つのベクトルに乗っているときは、両方を引用するのではなく再計算する。ただし引用するなら、**停止点と帯を名指しする**こと。両者の差の**大きさと向き**は、深刻度の帯・ベクトルの Threat 指標・比較している二つのフレームワークの**結合**で決まる。定数ではなく、フレームワーク単独の性質でもなく（§2a の `E:X` 対照群は Critical の **−0.35** から Low の **+1.2** まで動く）、一社の CNA の書き癖でもない。

## 1. 停止点とは何か

- **v3.1**：`TemporalScore = Roundup(BaseScore × E × RL × RC)`——平坦な積に対して**一度だけ** Roundup（FIRST v3.1 §7.2）。成分ごとに丸めると別の数になり、それは v3.0 型の記憶が生むものだ。テストに固定しておく重み：`E:F = 0.97`、`RL:O = 0.95`、**`RL:W = 0.97`**。
- **v4.0**：`E` は乗数ではなく MacroVector の一次元なので、`E:P` を表に与えたときの移動量は base がどこに座るかで変わる。同じ `E:P` が 10.0 では −0.7 点、4.8 では −3.9 点になる理由がこれである。
- **NVD のフレームワーク別の慣行**：2026-10-26 → 11-01 の窓で測ると、Threat 指標を持つ v4.0 指標 **136 件のうち 136 件**が **threat** スコアを格納し、**v3.1 では temporal 成分を 123/123 で剥がして** base を格納する。CNA コンテナは両列とも **base** を格納する。したがって「ベンダーは X、NVD は Y」は通常、一つのベクトルを二つの深さで引用したものにすぎない。

## 2. 実測した帯ごとの表（2026-11-03 20:22、一次）

母集団：NVD が **2026-11-02** に公開し、指標が `cna@vuldb.com` 由来の全レコード——**31** 件（当日の公開は合計 479 件）。NVD 呼び出し一回、追加予算なし。

| 事実 | 件数 |
|---|---|
| Threat 指標を持つ v4.0 ベクトル | **31 / 31**（`E:P` 29、`E:X` 2） |
| Threat 指標を持つ v3.1 ベクトル | **0 / 31**（NVD が剥がす） |

差 =（NVD の v3.1 base）−（NVD の v4.0 threat）。**3.1 の帯**で分割し、`E:P` の 29 件のみ。**符号は引き算の
順序で決まるので、この表の規約はツールと逆**である——§2a を参照。そこでは調査が **Δ = 4.0 − 3.1** を印字し、
同じ記録が −0.82 / −1.93 / −1.91 と読める：

| 3.1 の帯 | n | 差 |
|---|---|---|
| Critical（9.0–10.0） | 10 | **+0.7 × 8**、+1.3 × 2 |
| High（7.0–8.9） | 8 | **+1.8 × 7**、+2.8 |
| Medium（4.0–6.9） | 9 | −0.2、+2.2 × 4、+2.7、+3.9、+4.2 × 2 |
| Low（0.1–3.9） | 2 | +0.8、+1.4 |

平均 **+1.7**、範囲 **−0.2 … +4.2**。含意は二つ：

- **「4.0 のスコアは 3.1 より 0.7 低い」は Critical 帯の事実である。** これが引用されるのは、人が書くのが Critical のレコードだからで、Medium では差は 2〜4 点になり、一行では**符号が反転**する（−0.2：threat の削減とフレームワーク差がほぼ相殺）。
- **`E:X` の二行が別の理由で向きを反転させる。** `E` が未定義なら threat 効果は無く、v4.0 は 3.1 base より **1.0–1.6 点高い**——純粋なフレームワーク差であり、ベクトルを読まない人はこれを停止点の効果と誤認する。

## 2a. 帯の表がモードになり、2 つの効果を分ける対照群（2026-11-03 20:34）

上の手計算の表は草稿ファイルで計算されたもので、その**符号の規約がツールと逆**だった——同じ 31 件が
`Δ = v4.0 − v3.1` では **−0.82 / −1.93 / −1.91 / −1.1** と読める。これは `--pairs` が一貫して出してきた
規約であり、10-27 の週次調査が使った規約でもある（VulnCheck **+0.55**、VulnDB **−1.76**）。同じライブラリの
2 つの成果物が 1 つの事実に逆の符号を付けるのは、このファイルが存在する理由そのものの単位欠陥なので、
いまは調査自身がこの表を出力し、規約をヘッダに書く。

同じ日で新しいモードを走らせると（**2026-11-02**、NVD 1 ページ、455 指標、同源ペア **113**）、手計算の数字を
正確に再現し、手計算では作れなかった分解が増える：

| 割当者 · バンド | ペア数 | 4.0 が高い | 3.1 が高い | 平均 Δ（4.0 − 3.1） | Δ 範囲 |
|---|---|---|---|---|---|
| `cna@vuldb.com` · Critical | 10 | 0 | **10** | **−0.82** | −1.3…−0.7 |
| `cna@vuldb.com` · High | 8 | 0 | **8** | **−1.93** | −2.8…−1.8 |
| `cna@vuldb.com` · Medium | 11 | 3 | 8 | **−1.91** | **−4.2…+1.6** |
| `cna@vuldb.com` · Low | 2 | 0 | 2 | −1.1 | −1.4…−0.8 |
| `disclosure@vulncheck.com` · Critical | 4 | 1 | 3 | −0.35 | −0.6…+0.2 |
| `disclosure@vulncheck.com` · High | 37 | 24 | 12 | **+0.43** | −0.9…+1.7 |
| `disclosure@vulncheck.com` · Medium | 33 | 24 | 9 | **+0.67** | −1…+2.3 |
| `disclosure@vulncheck.com` · Low | 4 | 3 | 1 | **+1.2** | −0.8…+2.6 |

この表が 1 つの平均では買えない 3 つを与える：

1. **`E:X` はノイズ行ではなく対照群であり、VulDB にはほとんど無い。** VulDB の 31 ペアのうち **29 ペア**が
   `E:P`（残り 2 ペアが `E:X`）なので、その帯の表は *脅威効果 + フレームワーク差* をまとめて測っており、
   差をどちらにも帰属**できない**。VulnCheck の **78 ペア**はすべて `E:X` を明記するので、その行は
   **フレームワークだけ**を測る——そしてその差自体が帯に依存する：
   **−0.35（Critical、n=4）→ +0.43（High）→ +0.67（Medium）→ +1.2（Low）**。アジェンダの仮説
   （「3.1−4.0 の差は重大度が下がるほど広がる」）はこのきれいな対照の上で生き残るが、Critical のセルは
   逆符号で、背後には **4** ペアしかない。
2. **平均は 1 つの帯の中の符号の混在を隠す。** VulDB の Medium 行は **11 ペア、平均 −1.91、範囲 −4.2…+1.6**
   ——下が 8 行、上が 3 行。平均はそのどれも記述していない。だから件数を平均の隣に印字する。
3. **同じ日の窓に 2 人の書き手がいると符号が逆になる**（VulDB −1.51、VulnCheck +0.53）。同じフレームワーク、
   同じ日である。割当者を付けない比率は「その日誰が起票したか」の比率でしかない。

## 2b. コンテナ側、そして反転した問い（2026-11-03 20:34）

アジェンダの問いは「**VulDB 以外**のどの CNA が、Threat 指標を持つベクトルの隣に **base** の
`cvssV4_0` を保存しているか」だった。同じ日でコンテナ結合を付けて走らせると（`--with-cna 40`、
Threat 指標を持つ記録 32 件、読んだ記録/フレームワーク・ペア **61**、cveawg は課金なし）：

| 場所 | 件数 |
|---|---|
| `E` を持つ v4.0 ベクトルを公開するコンテナ | **32** |
| …**base** を保存しているもの | **29**——すべて `cna@vuldb.com` |
| …**threat** スコアを保存しているもの | **3**——**Qt**（`CVE-2026-107457`、`-100140`、いずれも `E:U`）と **HDFG**（`CVE-2026-120689`、`E:U`、HDF5 の再帰欠陥） |
| v3.1 コンテナ（NVD が `E` を剥がした 29/29） | **29**、すべて base、**0** ペアが不一致 |
| NVD ≠ コンテナの v4.0 ペア | **29**、Δ(nvd − cna) **−3.4…−0.7** |
| どちらかが算術に一致しないペア | **0** |

つまり問いの前提は逆だった。**base** を保存する習慣は **VulDB のもの**で、`baseScore` という名前の
フィールドに *threat* スコアを書いているのは **Qt** と **HDFG** である（名前は `cveawg` 自身の `assignerShortName` から取った——フィールドの UUID は orgId であって名前ではない）——そして NVD はその数字を **3/3** そのまま再現する。
これはツールがすでに印字している `loss` の場合（「コンテナが base でない数字を保存している」）と同じ
クラスである：フィールド名は型ではない。そして同じ日の窓に両方向が存在する。

## 3. この形を持つレコードは一つの CNA の書き癖である

この形を数えるのは三度目の窓で、そのたびに書き手は **VulDB** である：11-02 までの 26 時間で `cna@vuldb.com` の **41** 件（コンテナが base、NVD が threat を 41/41）、そして 11-02 の一日だけで 31/31。だから率は割当者と一緒に引用すること——「見たレコードの三分の一」はその日に誰が起票したかについての声明である。

11-03 のルーター群は同じ形を最高深刻度で見せている：WAVLINK のファームウェア 9 件と Linksys E8450 1 件が **2026-11-02T00:18:09Z → 06:17:43Z** に公開され、うち 8 件はコンテナで両フレームワークとも **10.0**、NVD は 10 件すべてに **4.0 の 9.3** と **3.1 の 10.0** を与え、状態は **`Deferred`**（誰も解析しない）。`affected[]` は**一つのファームウェア・ビルドを点として**名指しする（`{version: "V260507_2.0.0", status: "affected"}`、`lessThan` なし）ので、レコードが主張するのはそのビルドだけで、他については沈黙している——10.0 は当てにいけるパッチ範囲ではない。

## 2c. 差はまず**範囲**の事実であり、次に重大度の事実である（2026-11-05 12:40）

発端は Traefik の `CVE-2026-121966`。同一のソース（`disclosure@vulncheck.com`）が一つの不具合に 3.1 **8.7** と
4.0 **7.0** を並べた。4.0 のベクトルは `VC:N/VI:N/VA:N/SC:H/SI:H`——**脆弱なシステムへの影響はゼロ**で、すべて後続
システム側——一方 3.1 は `C:H/I:H` を脆弱なシステムに置き `AC` を `H` に上げている。これは**被害がどこに落ちるか**の
主張であって、どれほど重いかの主張ではなく、そもそも停止点でもない。

**v3.1 はこの形を表現できない。** `C/I/A` は影響を受けるコンポーネントを記述し、スコープ変更（`S:C`）は影響
サブスコアへの乗数にすぎない。v4.0 は同じ状況を二つの明示的な三つ組——脆弱なシステム（`VC/VI/VA`）と後続システム
（`SC/SI/SA`）——に分解する。つまり二つのフレームワークは同じ不具合について別の問いに答えている。

NVD の **2026-10-27 → 11-02** 公開ウィンドウで実測（3,418 metric、うち **610** レコードが**同一ソース**で両方の
バージョンの枠を埋めている。Δ = v4.0 − v3.1）：

| クラス（4.0 ベクトルが影響を置く場所） | 対 | 平均 Δ | 中央値 | 4.0 が高い | 3.1 が高い |
|---|---|---|---|---|---|
| `vuln-only`（`VC/VI/VA` のみ） | 441 | **+0.71** | +0.70 | 327 | 100 |
| `split`（両方の三つ組） | 53 | **−0.42** | −0.50 | 14 | 35 |
| `subsequent-only`（`SC/SI/SA` のみ） | 27 | **−0.89** | −1.00 | 1 | 25 |

**クリーン部分集合：610 中 521。** 除外した 89 対は停止点の交絡であって些事ではない——4.0 ベクトルが生きた `E` を
持つ（または 3.1 の点数が base 以外で保存されている）対は §2a がすでに答えた問いである。これを外すことで VulDB は
**−1.29** から、生き残った 16 対の `vuln-only` で **+0.87** になる。あの CNA の負の平均はすべて threat 項だった。

v3.1 自身の語彙への対応はほぼ全数で、だからこの効果は採点の癖ではなくフレームワークの事実として読める：
**`S:U` → `vuln-only` 440/443**、**`S:C` → `split`/`subsequent` 77/78**。しかも符号は**単一の採点者の中で**クラスに
従う——VulnCheck のクリーンな 456 対は **+0.74**（`vuln-only`）、**−0.65**（`split`）、**−0.83**（`subsequent-only`）
——「4.0 の列が低い」は書き癖でも重大度のドリフトでもない。

**フィードにとっての意味：** 二列の項目が「3.1 は 8.7、4.0 は 7.0」と書いてドリフトと呼ぶとき、それはフレームワークの
スコープの問いを述べている。書くべきはどちらのベクトルが影響をどこに置くかであり、**ローカル**な不具合を後続システム
の数字で切り分ける読者は、二つの異なる配備姿勢を比べている。

## 4. 読み方の規則

1. **二つの数を比べる前に `E` を探す。** 同じベクトルで停止点が違う＝不一致ではない。`E:X` か不在なら、差はフレームワークであり threat ではない。
2. **散文で停止点を名指しする**（"a base of 10.0 and a threat score of 9.3"）——引用したスコアがある停止点に整合するのに項目がそれを名指ししないとき、lint の `score-stopping-point` 勧告が出る。
3. **二つの停止点を平均しない**し、NVD が CNA のベクトルを再給仕しただけのときに低い方を「NVD の見解」と呼ばない。
4. **差の向きから停止点を推測しない**——Medium 帯では二つの効果が逆符号で、相殺しうる。
5. **ドリフトと呼ぶ前に 4.0 ベクトルの `SC/SI/SA` を読む。** 後続システムへの影響が少しでもあれば、4.0 の数は**別の配備姿勢**であり、3.1 の方が通常高い（§2c：そうした 80 対のうち 60 対）。デルタではなくクラスを名指しする。

## 5. 一つの呼び出し

```
node agent/tools/cvss-recompute.mjs --ids CVE-…,CVE-…            # 再計算。v4.0 は --oracle が必要
node agent/tools/cvss-recompute.mjs --from YYYY-MM-DD --to YYYY-MM-DD --stopping-point-census \
     --with-cna N [--oracle /path/to/cvss4] [--per-page 1000] [--json]
node agent/tools/cvss-recompute.mjs --from YYYY-MM-DD --to YYYY-MM-DD --scope-census [--json]
node agent/tools/claim-unit-lint.mjs --check cvss --file en/feed/YYYY-MM-DD.md
```

v4.0 のオラクルは意図的に同梱しない MacroVector 表である。無ければツールは判定ではなく `v4-not-recomputed` を印字する。`judge()` は**どの**停止点に一致する数も受け入れるので、正直な threat スコアが再現不能として報告されることはない。

## 6. 双列ギャップの方向はレコードごとに反転する——Craft と Scriban がスコープ読みをウェーブ規模で再確認

VulnCheck の 11-08 ウェーブは各レコードを二度公開——`Primary` CVSS 3.1 の隣に `Secondary` CVSS 4.0——そしてギャップの**符号は CNA の定数ではない**：Craft の 6 件の新レコードは 9.8→9.3、6.5→7.1、7.5→8.7、8.8→8.7（同一 CNA、同一日で両方向）、Scriban の 3 件は逆に走る（**+1.2–1.7**、7.4→9.1）。これは §2 のスコープ国勢調査がウェーブ規模で繰り返されたもの：4.0−3.1 の符号は**影響がどこに着地するか**に従う（521 のきれいなペアで：vuln-only +0.71、subsequent-only −0.89、split −0.42）、ゆえに「この CNA の 4.0 は高い/低い」というウェーブ級の主張は、ウェーブがたまたま含んだスコープ クラスについての**構成的主張**——Scriban のテンプレートは影響を脆弱なシステムに置き、Craft の GraphQL バイパスはそれを分割する。二つの執筆ルールが落ちてくる：すべてのスコアの隣にバージョンを引用すること；そして同一 CNA のウェーブが同日に両方向で自分自身と食い違うとき、その食い違いこそが発見——平均して消せる誤植ではない。
