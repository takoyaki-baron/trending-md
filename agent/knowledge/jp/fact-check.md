# ファクトチェック手法

トレンド項目をフィードに載せる前に検証する、再利用可能な公開前メソッド。`CLAUDE.md`の
ソース検証ルールと2026-08-12のVoidの教訓から抽出した。これは学習エージェントの最も重要な
再利用可能アセット——一次シグナルと再利用された二次集計を分けるもの。

## 中核原則

**集計メトリクスは「調査せよ」というシグナルであり、「公開せよ」というシグナルではない。**
スター数、トレンド順位、「+2,840 stars」という行は、何かが動いていることを教えるだけで、
「なぜ」も、それが本物かどうかも決して教えない。速度は項目に調査キューへの席を与えるに
すぎない。記事そのものは、ページを開いて初めて獲得できる。

## 公開前チェックリスト

項目を書く前に、この3つのチェックを実行する：

1. **リポジトリ自体を開く。** README、最終コミット日、`archived`フラグ、メンテナンス状況。
   スター数だけでは、プロジェクトが生きているか、放棄されているか、古いブログ記事で一時的に
   バズっているかは分からない。
2. **引用しようとしているすべてのソースリンクをクリックする。** そのページは、帰属させようと
   しているデータポイントを実際に含んでいるか。ツールのランディングページはデータソースでは
   ない。検索結果ページも、特定の事実のソースではない。そのデータがページ上に見つからなければ、
   引用しない。
3. **メトリクスではなくトリガーを見つける。** リポジトリが急上昇するのには理由がある——新
   リリース、HNでの言及、スレッド、ブログ記事。そのトリガーを見つけ、それを軸に項目を書く。
   「Xの休眠エディタがHNの言及で再浮上」は正確。「Xが2位に急上昇」は文脈がなければ誤解を招く。

## ケーススタディ：Void（2026-08-12）——2つの失敗、1つの根本原因

- フィードは`voideditor/void`を+2,840 starsでトレンド2位と見て、「Cursor/Copilotを超える
  AIファーストエディタの勢い」と書いた。
- **GitHubも引用されたPageCrawlページも実際には開かれなかった。** リポジトリを開いていれば：
  READMEには「2025年半ばから開発休止」とあり——プロジェクトは死んでいる。PageCrawlリンクを
  クリックしていれば：それはVoidのデータを一切持たない汎用ツールのサインアップフォームだった。
- **根本原因：** 実際のページを訪問せずに集計メトリクスを信頼したこと。これは単一項目における
  二層の偽シグナル——順位は誤りで、引用された「ソース」は何も裏付けていなかった。

## ケーススタディ：正しくやる場合（今回のCVE検証）

同じ規律を[[agent-stack]]の2つのセキュリティ項目に適用すると、1行のフィード要約が正味
新しい一次ディテールに変わる：

- **mcp-grafana CVE-2026-19516（SSRF）**——フィードの「呼び出し元制御の`X-Grafana-URL`ヘッダー」
  はCVEレコードと照合して一致し、開いてみるとより深いストーリーが浮かぶ：CWE-918、そして
  *関連する前身*（CVE-2026-15583、「混乱した代理人」トークン流出）——その修正はトークン漏洩を
  塞いだが宛先は**制限しなかった**。それがまさに19516が依然として成立する理由。単一の修正は
  十分でないことが多い。
- **Langflow CVE-2026-9198（RCE）**——フィードの「auto_login + validate/code」は実際には*2つの*
  独立した欠陥の連鎖（CVE-2026-9103 認証バイパス + CVE-2026-8481 サンドボックスなし`exec()`）で、
  エクスプロイトはデフォルト引数のトリック（`def _v(a=exec('<payload>')): pass`）を使う。
  なぜならPythonはデフォルト値を定義時に評価するから。検証はスコアではなくメカニズムを開いた。

要点：ファクトチェックは偽項目を取り除くだけのゲートではない——薄い要約を、フィードが本来
届けるべきディテールへと変換するメカニズムなのだ。

## ケーススタディ：GenLayer（2026-08-19）——Voidの失敗モード、公開前に捕捉

トレンド順位が測っているのは**エンジニアリングではなくインセンティブ**だという、これまでで最も明確な実証——
そして上記のチェックリストが初めて端から端まで機能し、項目を殺すのではなく*ストーリーを変えた*事例。

- **集計が言うこと：** `genlayerlabs/genlayer-project-boilerplate` が **GitHub Trending（デイリー）12位、本日
  +543 stars、合計15,898**。
- **チェック1——リポジトリを開く（GitHub APIで検証、8月19日）：** `pushed_at` **2026-07-26**——24日間コード活動
  ゼロ——77コミット、**公開リリースなし**、`description: null`、800フォーク、アーカイブされていない。再チェック
  時のスター数15,901。内容はデモで、「the boilerplate code for a GenLayer use case implementation, specifically
  a football bets game.」
- **チェック3——トリガーを見つける：** GenLayerはインセンティブ付きテストネットのポイントプログラムを運営して
  おり（Builder/Validator/Communityトラック、Stewardがレビューし「新規性・複雑性・影響」で採点）、第三者の
  エアドロップガイドはGitHubリポジトリにスターを付けるのが最初のポイントを記録する最速の方法だと読者に伝えて
  いる。つまりトリガーは*ポイントプログラム*であり、リリースではない。
- **チェック2——ソースをクリックする：** ここでチェックリストが報われた。GenLayer**自身**のIncentivized Builders
  Program発表を直接読み、**GitHubスターのアクションは一切リストにない**。トークンもエアドロップも確認されて
  いない。エアドロップガイドのフレーミングは一次ソースで裏付けられなかった。
- **公開されたもの：** 集計のフレーミングではなく*食い違い*——「スターでポイントという主張はエアドロップガイドの
  アグリゲータに現れ、我々が読んだGenLayer自身のプログラム投稿にはない」。2つの曲線は完全に切り離される：
  **1日で543スター、対して24日間コミットゼロ。**

**これがVoidに付け加える教訓：** Voidは*死んだ*プロジェクトに生きたスターが付いていた。GenLayerは*生きているが
非アクティブなデモ*にインセンティブ付きスターが付いている。原因は違うが根は一つ：スター曲線とエンジニアリング
曲線は独立変数なのだ。そして二次ソースと一次ソースが食い違うとき、「食い違いを報告する」ことはどちらの版よりも
強い項目になる——検証可能な形で真である唯一のフレーミングだからだ。

**系——発表会場の主張もチェックする。** 同じバッチで、`RyanCodrai/turbovec` は基盤となるTurboQuant論文を
「ICLR 2026」と引用していたが、arXivレコード（2504.19874）には会場採択が記載されていない。発表会場は他の
引用可能な事実と同様の事実であり、READMEがそれを主張するだけではソースにならない。

## 公開後の訂正（メソッドのもう半分）

ファクトチェックは公開前のゲートだけではない——同じ規律は、項目が*公開され*、後に間違いと判明
した場合にも適用される。feed訂正の慣例（Void訂正の後に`CLAUDE.md`へ成文化、2026-08-13）は、この
メソッドの公開後側の半分である：

1. **本文をその場で修正する**——項目の番号と位置を保ち、タイトル/説明を実際に真実である内容へ
   書き換える（「トレンド」ではなく「アーカイブ済み・非推奨」）。番号を振り直したり、黙って削除
   したりしない。
2. **不正なリンクを撤回する**——帰属された事実を一度も含まなかったソースを除去し、実際に訪問した
   ソース（リポジトリ自体、本当のベンダーページ）に置き換える。
3. **有効なリンクを≥2保持する**——訂正された項目にも、訪問済みで機能するソースが少なくとも2つ必要。
4. **速度を再導出する**——訂正された項目の速度は現実に合わせて下がる（▮ steady）。膨らんだ順位を
   決して保持しない。
5. **zh/ と jp/ へ反映する**——訂正は同じ実行で3つのロケールすべてに反映される。

統合されたメソッド：**公開前に検証し、発見後に訂正する。** 両方とも一次ソースを訪問するところから
始まり、集計のフレーミングからは始まらない。Voidは前半の常設例（公開前に捕捉）、その場での訂正は
後半の常設例（公開後に捕捉）。

## いつ適用するか

毎バッチ、公開前に：各項目にチェックリストを実行する。3つのチェックをすべて完了できない項目は
「未検証」として扱い——チェックを完了させるか、項目を落とす。Voidの教訓は常設の警告として
残しておく。それが、このメソッドが存在するまさにその失敗モードなのだから。

## 8月19日 20:03 バッチからの系論

「ソースを確認し、集計を信じるな」の3つの追加実例、各項目につき1つ：

- **Oracleのパッチ数——ベンダーの数字を報告する。** 8月のCSPU項目は「925 CVE / 154 critical」として流通するが、
  Oracle自身のアドバイザリは**943個の新規セキュリティパッチ**と述べる。引用するのはベンダーの数字。第三者の
  集計はそれと一致しない。
- **OpenZFS OZ-1 —— 実際に読んだリストを引用する。** 並走する `hotmolts.com` の記事はクライアントレンダリングで、
  サーバー側は技術内容を一切返さなかったため、項目は実際に読んだ oss-security メーリングリストの投稿を引用する。
- **Mojoのライセンス——検出器はソースではない。** GitHubのライセンス検出器は `modular/modular` に `NOASSERTION`
  を報告する（LLVM例外が自動検出を妨げる）。「Apache-2.0」という主張はModular自身のもので、実際に読んだ発表に
  記されている。ライセンス主張にはベンダーの声明が必要で、検出器ではない——turbovecの「ICLR 2026」会場の系論と
  同形。

## 訂正には2つの種があり、ベロシティへの帰結は正反対である（08-20）

このチェックリストを**自分自身の**フィードに適用したところ、1つのバッチで2件の誤りが見つかった。
両者は似て見える——どちらも「項目が誤っていたので、その場で直す」——が、同一に扱うと台帳はかえって
悪くなる。この区別はいまや手法の一部であり、`CLAUDE.md` の訂正規約もそれに合わせて改訂した。

### 種1——主張の誤り（フレーミングが誤っていた）

**事例: `akitaonrails/ai-memory` をDHHに帰属（2026-08-20、項目21）。** フィードは
「DHHのRustエージェントメモリ」と題していた。GitHubのオーナープロフィールには **Fabio Akita**
——Codeminer 42、ブラジル、フォロワー19.5k——とある。DHHは `dhh`（David Heinemeier Hansson、
37signals）であり、その作品は**同一フィードの項目9であるOmarchy**だ。Railsコミュニティの著名人2名が、
1つのファイルの中で1人に潰れていた。

なぜベロシティの再導出に値するのか: その誤帰属は**仕事をしていた**からである。
「DHHがエージェントメモリを出した」がニュースになるのはDHHが誰であるかによる。
「著名なブラジル人Rails開発者がエージェントメモリを出した」はより小さな話だ。
順位の一部は誤りによって買われていたのだから、順位は返さねばならない——
▮▮ rising → ▮ steady、タイトルと本文の修正と併せて。

**もっと早く捕まえられたはずの検出ルール:** `owner/repo` というスラッグは**人物に関する検証可能な主張**である。
API1回（`/users/<owner>`）で決着する。プロジェクトが属するコミュニティ、言語エコシステム、
あるいは同じバッチの別項目から著者を推測してはならない。

### 種2——引用の誤り（リンクが誤りで、話は正しい）

**事例: GrapheneOSのMastodonパーマリンク（2026-08-20、項目18）。** 引用された投稿は **404** を返す——
HTMLページとMastodonのステータスAPI（`/api/v1/statuses/<id>` → `{"error":"Not Found"}`）の
二通りで確認した。しかし**話そのもの**——GoogleがPixelカーネルおよびユーザー空間ドライバーのGitタグを、
Googleフォーム → 人手による承認 → Drive上の履歴を剥いだtarball、へ置き換えたこと——は事実であり、
Android Authority（8月10日）、securityonline.info、ITHome、OSChinaほかにより独立に裏づけられている。
同じ方法で確認した姉妹項目15のGrapheneOSパーマリンクは正常に解決し、しかも二次報道より**多くの**内容を
含んでいた。

なぜベロシティを再導出しては**ならない**のか: この項目の目立ち具合は、そのURLに一切依拠していない。
HNスレッドの647ポイントは本物で、話も本物だ。ベロシティを下げることは、リンク切れへの罰として
フィードに本物のトレンドを過少報告させることになる——逆方向の誤りである。

修正はより狭い: 誤ったリンクを撤回し、**実際に開いた**情報源（Android Authority）に差し替え、
有効なリンクを2本以上保ち、そのことを項目内に明記する。

### ルール

| | 主張/フレーミングの訂正 | 引用の訂正 |
|---|---|---|
| 何が誤りだったか | 事実またはフレーミング | ポインタのみ |
| 修正 | タイトル＋本文を書き直す | リンクを差し替える |
| ベロシティ | **再導出**（通常 → ▮ steady） | **維持** |
| 根拠 | 誇張されたフレーミングが順位を押し上げた | 順位はそもそもリンクとは無関係 |

「訂正された項目は一律steadyへ下げる」を両者に機械適用すれば、台帳は静かに劣化していた。
この規約は**誇張された**順位が訂正を生き延びるのを止めるために存在するのであって、
あらゆる編集を罰するためではない。

### これによりチェックリストに加わる2つの習慣

1. **記事URLだけでなく、あらゆるパーマリンクを解決すること。** ソーシャルメディアのパーマリンク
   （Mastodon、X）はフィード中で最も脆い引用である——投稿は削除され、IDは書き写しを誤られ、
   インスタンスは移転する。ステータスAPIは1回の呼び出しで済み、曖昧さのない答えを返す。
2. **アグリゲータの抜粋だけでなく、一次アカウント自身のタイムラインを読むこと。** **有効な方の**
   GrapheneOSパーマリンクを確認したところ、報道が省いていた材料が返ってきた——2027年の初期デバイスは
   フラッグシップで「Pixelより高価で高性能なハードウェア」、Qualcomm次第であり、
   Motorolaにより長い更新への支払いを促す必要がある——加えてフレーミングへのプロジェクト自身の反論:
   「デバイスが2027年になるというのは、実のところニュースではない」。検証と報道は同一の行為である。
   合否しか返さない検証は、使い切れていない。

## 鮮度もファクトチェック：3日の重複排除ウィンドウが3件の繰り返しを見逃した（08-23 04:03）

08-23 バッチは既出の3リポジトリ——`AprilNEA/OpenLogi`（08-19）、`jundot/omlx` と `AlexsJones/llmfit`（08-18）——を*新規*発見
として再掲した。根因は幻覚ではなく機械的：`generate-feed.sh` が3日間の直近履歴ウィンドウしか渡しておらず、三者とも4〜5日前
だった。教訓：「これは本当に新しいのか？」は*プロンプトが実行可能でなければならない*チェックである——重複排除ウィンドウが
トレンドリポジトリの自然な再出現リズムより短いと、更新が黙って重複へ変わる。修正済み：ウィンドウを7日に拡大し、「日付付き更新
としてのみ扱い、新発見とはしない」という明示ルールを追加。

## ベンダーの悪用可能性フラグはクラウド CVE で唯一検証不能なフィールド（08-23 04:03）

CVE-2026-69836（Microsoft Entra ID、CVSS 10.0）は「Exploited: Yes」で公開され、翌日「No」へ戻された。一次読みの MSRC
レコードは現在 `exploited: No`、CVSS 3.1 ベクトル `…/E:U`（**悪用未実証**）、`customerActionRequired: false`。*クラウド
サービス* CVE には検査可能なパッチ成果物がない——悪用フラグが唯一の信号であり、それはベンダー発行の可変フィールドであるため、
完全に緩和済みのクラウド CVE について「悪用されているか？」は第三者には原理的に検証不能。唯一の独立した手がかりは定性フラグを
時間メトリクス（`E:U`/`E:POC`/`E:F`/`E:H`）と突合すること。「ベンダーを信じ、アグリゲータを信じるな」と同じ形で、一段手前。
