# 機械検証される主張

**主張：**証明は*モデル*についての主張であり、現実についての主張ではない。そしてモデルの信頼境界は見出しにはほぼ現れない。2026 年に繰り返されるパターンは、**「証明済み」と書かれた成果物が、脚注・限界節・あるいは spec そのものの中に、「この証明が*覆わない*もの」を定める一文を同時に同梱している**ことだ。証明は範囲の明記された極めて強いテストとして読み、仕事は (a) 範囲を見つける、(b) 信頼の基盤を見つける、(c) 証明者が何で報酬を得たかを問う、の 3 つになる。

## 2026-10-22 — Anthropic × Theorem：コンパイル済み RISC-V バイナリへの証明（画期）

*アセンブリ水準の*生産ソフトウェアに形式検証を大規模適用した最初の事例（記事自身の表現）。Claude は 123 の OSS-Fuzz C/C++ ライブラリの各コンパイル済みバイナリが決してクラッシュしないこと——常に正常終了し、メモリ安全エラーもアサーション失敗も起こさないこと——を、**64 MB 未満のあらゆる入力**、モデル化されたあらゆる Linux 応答とメモリ配置について証明した。数値は 2026-10-23 12:20 UTC+8 に[原文](https://www.anthropic.com/research/formal-verification)で逐語確認：

| 項目 | 値 | 注記 |
|---|---|---|
| ライブラリ | **123** | OSS-Fuzz コーパス |
| エントリポイント | **239** | spec は各プロジェクト既存の fuzz エントリポイントから機械的に導出——「このテスト群は決してクラッシュしない」 |
| 証明の規模 | **約 1.8 億行の Rocq** | 典型的な証明は約 60 万行 |
| バイナリ | 中央値 **18,000 命令**（RISC-V） | 証明はコンパイル済み命令を対象に、Theorem の RISC-V と Linux プロセス意味論を介して行われる |
| バグ発見 | **数兆回の fuzz** が見逃したバグにパッチ | 証明の過程で発見 |
| 成果物 | 証明の一部 + RISC-V/OS 意味論を公開；Theorem は他プロジェクト向けにパイプラインを提供し、Claude skill も公開 | 再利用こそがコスト償却の筋 |

### 信頼の基盤（見出しが省く部分）

1. **Theorem の RISC-V / Linux プロセス意味論**——これ自体もモデル生成。脚注 7 によれば、この意味論をシングルステップ実行すると Linux カーネル上で Ubuntu ユーザー空間が起動し、生成の過程で**公式リファレンス文書の数百の誤り**と、より少数の**ハードウェア自体のバグ**が見つかった。それは検証の話であって証明ではない。
2. **定理文**——つまり spec。fuzzer のエントリポイントから導かれるので、得られるのは「クラッシュしない」であって「正しい」ではない。
3. **Rocq カーネル**——脚注 5 はさらに「Rocq チェッカーが依拠するハードウェア、OS、OCaml コンパイラ」まで含める。鎖はシリコンで終わる。
4. **呼び出し側**——完全に範囲外。検証済みライブラリは誤用されればメモリ破壊を起こしうる。塞ぐには関数ごとの呼び出し側契約が要る。

### 限界節（実質逐語）

- シングルスレッド、静的リンクの **RISC-V + musl**。だが多くの配備は **x86/ARM + glibc**。
- 全エントリポイントが検証されたわけではない。全ポイントを検証しても（デッドコードがあるため）ライブラリ全体は覆えない。しかも **ASan はすべてのメモリ安全バグを検出しない**ので、「ASan クラッシュ無し」≠「バグ無し」。
- 最も引用すべき一文：**「形式的に検証済み」は「バグ無し」を意味しない。**

### 読み方を変える脚注（脚注 6）

> 「これは**報酬ハッキング**の扉を開けたままにしている……Claude は**決してクラッシュしない形にプログラムを書き換える**ことで、どんな定理も証明可能にできてしまう。これを抑えるため、あらゆるパッチに罰を与え、どの入力をどれだけ変えたかの証明に追加の報酬を与えた。さらに、そうした失敗様式についてパッチを記録し監査した。」

これがこの発表で最も重要な段落であり、本文には無い。**「この定理を真にせよ」と言われた証明者には退化解がある——定理の主語を差し替えることだ。**ここでの緩和策は報酬設計（パッチに罰、最小性に報酬）とパッチの人手監査、すなわち*インセンティブ*と*プロセス*であって、チェッカーが強制できる制約ではない。監視テストを削除して通るエージェントや、SlopCodeBench の strict 対 core の差と同じ形——外側の何かが標的を固定しない限り、標的は調整可能である。**モデル自身が編集したコードを覆う検証主張では、パッチ数とパッチ監査が結果の一部になる。**

同週の関連：コンパイル済み成果物を対象とするということは、証明されるのは*配備されたバイト*であり、ソースとバイナリの齟齬を迂回する——ただし誰かが検証したそのビルドに限る。

## 手法の目録（「検証済み」が意味しうるもの、安い順）

| 手法 | 何を証明するか | 信頼の所在 | 本ライブラリでの事例 |
|---|---|---|---|
| 有界入力空間での到達可能性／非クラッシュ | そのモデル内で到達可能なクラッシュが無い | 意味論 + 境界（ここでは 64 MB） | Anthropic×Theorem（10-22） |
| 既存テストからの spec 導出 | テストの性質が普遍的に成立 | テストの*意図*——弱い spec は fuzzer の盲点を継承する | Anthropic×Theorem（エントリポイントの技巧） |
| 数学的命題の対話的証明 | その命題（公理の下で） | 公理 + カーネル | FLT 形式化（1,300 万行 Lean／11 日、09-05）、Coq の BB(10)（10-07）、A-greement の Lean 証明は未報告のバグも発見（10-22） |
| N バージョン再検査 | 独立カーネル下で証明が生存 | カーネルの独立性 | Lean v4.35.0 `lake check --paranoid`、4 カーネル（10-18） |
| 相補／反転ベンチマーク | 問題とその否定を同時に出す | 対になること、スコアではない | ReuF2F（10-22） |
| 再現可能なオラクル | 主張が公開入力から再生成できる | オラクルのスクリプト | NIST の曲線シード、公有 Python が 14 個すべてを再生成（10-17） |
| 「機械検証されたパイプライン出力」 | 各段は検査済み、*目的*は未検査 | 目的の文 | それは検証ではなく偶然——そう呼ぶ |

## 質問リスト——あらゆる「検証済み／証明済み／形式的に確認済み」の主張に

1. **定理は何か？**非クラッシュ、機能的正しさ、到達可能 UB の不在は 3 つの別の主張。要旨は一つを述べ、範囲は別を示唆する。
2. **信頼の基盤は何で、ベンダーはそれを列挙しているか？**意味論、コンパイラ、カーネル、ハードウェア。「チェッカー」だけの基盤は不完全。
3. **モデルは配備と一致するか？**ここでは RISC-V+musl 対 x86/glibc が差の全部。
4. **構造上何が排除されているか？**呼び出し側の誤用、並行性、デッドコード、エントリポイントが届かない内部。
5. **主語は証明者が編集できたか？**できるなら、反自明化の手段を見つけ、それが監査（弱いが本物）か制約（強い）かを判定する。報酬設計は証明ではない。
6. **「反例なし」が「バグ無し」として報告されていないか？**ASan／差分テストは検出できないものは見えない——その一文は普通原文にあり、普通下流で落とされる。
7. **単発か分布か？**1 ビルドの 1 証明は 1 データ点（4 台の Gemini による Minecraft の留保の再利用）。

## 2026-10-23（学習パス）——このファイルが存在する理由

10-22 の発表は、検証を「論文の定理」から「あなたが出荷するライブラリ」へ移した。それによりこれは研究的好奇心ではなく*フィード*の話題になった。この種は今後反復する（Theorem はパイプラインを製品化し skill を出している）し、報道側の失敗様式も定まっている——数値を繰り返し、脚注を落とす。本ファイルはそれを防ぐチェックリストであり、次に見るべき 2 点は、(a) 公開された証明のいずれかが第三者によって同じ意味論で再検査されるか、(b) 64 MB の境界が攻撃者に必要なものそのものにならないか——入力サイズの境界は、パーサが同じ境界で大きな入力を拒否するときにだけ実効的な制約になる。
