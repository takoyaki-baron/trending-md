# ハーネス・オーバーヘッド——ハーネスが請求明細の行を持たずに使う二つの資源

ハーネスは、頼まれた仕事について課金し、その裏で別の二つを払っている。**自分自身を記述するために使うトークン**と、**すでにやったことを再確認するために使う注意**である。どちらもユーザーの発した要求には現れず、タスクの大きさではなくセッションの長さに比例して増える。2026-10-29 20:00 のバッチはその両方を測った——一方は請求額に占める割合として、他方は欠陥の後の失敗率として。

隣接ファイル：[[harness-reliability]]（同じ継ぎ目を障害注入・StateMirror・HarnessMM で測ったもの）、[[token-economics]]（コスト境界。キャッシュ読み取りがエージェント的支出の 96–99%）、[[agent-stack]]（製品カテゴリとしてのハーネス）、[[fact-check]]（自己申告の表の読み方）、[[frontier-models]]（ベンチマークの列としてのハーネス）。

**主張：** ハーネス自身の簿記は、タスクと同じ二つの資源を奪い合う。そしてそれぞれの有用な単位は、*費やされているものに占める割合*——支出の 16.4%、見逃された欠陥の 95%——であって、呼び出しあたりのコストではない。**結果**（信頼度ではなく）で価格づけする方針と、記憶を**層状**（一括ではなく）に開示する設計が、現在の両者への最良の答えである。

## 1. トークンのオーバーヘッド：請求額の六分の一を払う一行のステータス

**Claude Code の `agent_summary`**（flamerix.ai による測定、2026-10-29）。約 30 秒ごとに、**バックグラウンドの各エージェント**について、クライアントはそのエージェントの**転写全体**をそのエージェント自身のモデルへ送り、「直近の行動を **3〜5 語**で説明せよ」と尋ねる。答えはエージェントパネルの一行を更新するだけで、モデルにも会話にも届かない。**2.1.232**（2026 年 8 月）以降デフォルトで有効で、「**それを切る設定は存在しない**」——リンクされた issue はまさにその設定を求める*機能要望*である（[anthropics/claude-code#86879](https://github.com/anthropics/claude-code/issues/86879)、2026-08-15 起票、未クローズ）。

測定はクライアント自身の **OpenTelemetry** エクスポートを `query_source` でグループ化したもの：

| 指標 | `query_source = agent_summary` | メイン会話 |
|---|---|---|
| Claude Code の全支出（`cost_usd`）に占める割合 | **16.4%** | 15.7% |
| 全 API リクエストに占める割合 | **19.7%** | — |
| その支出のうち Opus に向かう割合 | **96%** | — |

入出力比は約 **9,000 : 1**——要約器は三語を書くために転写全体を読むので、コストは**コンテキスト長**に比例する。だからこの比は細部ではなく機構そのものである。issue スレッドには**四つの独立測定が 18–26%** として集まっており、擁護できる文は「**六分の一から四分の一**」であって「16.4%」ではない。

**単位、そしてこの主張がたいてい壊れる場所：** 16.4% は Claude Code **自身の `cost_usd` 推定**に対する割合であり、請求書に対する割合ではない。サブスクリプションでは失われるのは**レート制限の余裕**であって金ではない——出典自身がそう書いており（"if you are on a subscription, what you lose is rate-limit headroom"）、要約記事はたいていそれを落とす。

**計測の手法はこのクライアントの外にも一般化する。** フックは約 80 行の **Bun プリロード**（`BUN_OPTIONS=--preload`）で、`setTimeout`/`setInterval` をラップし、コールバックのソース文字列が要約器のアンカーに一致したとき不活性なハンドルを返す。モジュールが**プリコンパイルされた Bun バイトコード**として配布されていても機能する——バイトコードから実行されても `Function.prototype.toString` はコールバックの**ソース文字列**を返すので、タイマーは同一性ではなく*内部の文字列*で識別できる。バンドルされたランタイムはどれもこの性質を持ち、両方向に効く：文書化されていないタイマーを見つける方法であり、同時にマッチが脆い理由でもある。

**出典は自身の fail-open 一覧を公開している**（これが引用可能にしている部分だ）：ログ行や query-source id の改名、`fn.bind(...)` 経由のコールバック（`toString` にソースが無い）、アンカー文字列をコールバック外の共有定数へ移動、タイマーがラップされない API（`timers/promises`、スケジューラループ）へ移行。**Tested versions** 表は 2.1.257 → 2.1.312 を覆い、約 2.5 分のエージェント実行あたりの summary fork 回数がフック無し／フック通過／フック無効で **5 / 5 / 0**——つまりフックは「入った」と主張するのではなく、*防いだ fork を数える*ことで検証されている。

## 2. 対抗設計：記憶を層で開示する

**`thedotmack/claude-mem`**（104,222★、9,193 fork、Apache-2.0、作成 2025-08-31、最終 push 2026-10-29——一年以上経つプロジェクト、一次確認済み）は同じコスト問題を保存側から解く。その検索は「埋め込んで返す」ではない。三層の MCP ツール——

1. `search` → ID 付きの簡潔な索引（**1 件あたり約 50–100 トークン**）、
2. `timeline` → 生き残った項目の前後の時系列、
3. `get_observations` → **絞り込まれた ID のみ**の完全な詳細（**1 件あたり約 500–1,000 トークン**）。

エージェント記憶の故障モードは再現率ではなく**コンテキスト費用**なので、二段のフィルタは高価なトークンをモデルがすでに選んだ行にだけ使う。距離を置くべき主張は二つ：README の「**約 10× のトークン節約**」の背後にベンチマーク節が無い（プロジェクト自身の数字として引用する）、そして二つのトークン幅は**推定**であって測定ではない。

噛みつくインストール細節が二つ：`npm install -g claude-mem` は「**SDK/ライブラリのみ**——プラグインのフックを登録せず、ワーカーサービスも設定しない」（グローバル導入は成功に見えて何も届けない）、そしてある対応ホストでは既定が**CMEM Pro**（ホスト型の記憶）で、ローカル観測器は明示的な opt-in（`--provider host`）——専有リポジトリに向ける前に読むべき文である。

## 3. 注意のオーバーヘッド：誰も読み返さない欠陥

**FeatureArc**（arXiv 2610.37434、2026-10-27 投稿；**Hunyuan Team, Tencent** + 香港中文大学——所属は要旨頁ではなく HTML 全文から読んだ）が評価するのは、エージェント自身の先行作業の**後**に来る要求である：**10 個のコーディングエージェント**、**73** 件の手作業で精査されたタスク、各 **2〜10 段階**、単一の永続セッションとワークスペース、**外部テストのフィードバック無し・ロールバック無し**。

| 測定 | 値 |
|---|---|
| 第一段階のプール成功率 | **62.7%** |
| 最終コード上で機能全体を試したときのプール成功率 | **28.5%** |
| 後段の失敗に**継承欠陥**が含まれる割合 | **72.9%** |
| 失敗に続く段階で、先行する誤りが**気づかれないまま**の割合 | **約 95%** |

この 95% が、失敗を能力から**注意**へ移す：第 4 段階のエージェントは第 4 段階の要求で失敗しているのではなく、再確認する手順を持たない土台の上で正しく作っており、自己テストは初期段階をほとんど見返さない。これは**これらのシステムの配線**——追記のみの履歴、現在のステップにだけ及ぶテスト——についての陳述であってモデル品質ではない。ロールバック無しの設計が、「待って、火曜のキャッシュ無効化は誤りだ」と言うはずの人間を取り除いている。

信頼性の注記二つ：このパイプラインはベンダー**自身**の評価装置であり（「内部評価をこの設定へ拡張し、Hunyuan の開発を導く」）、エージェント別の表は自己測定として読む。そして 73 タスク・実履歴から採った段階は小さく、「逐次的な機能開発はこのハーネスで劣化する」とは言えるが、10 エージェントの順位付けには足りない。

## 4. 信頼度ではなく結果で価格づける制御

**CASEL**（arXiv 2610.36570、2026-10-27 投稿）は不確実性の閾値を、呼び出しごとの六モード選択——直接実行・検証・サンドボックス・確認・承認・棄権——に置き換え、較正された失敗確率、**状態依存の結果、可逆性、曖昧さ、証拠の鮮度**から成る**モード別コスト**を最小化する。

- 統制されたシミュレーション、**20 シード × 各 120,000 テスト行動**、"every method has the same intervention menu and **the same compute cost**"——比較対象は不確実性で並べたゲート。
- 有害副作用のある軌道 **14.75% → 7.02%**、平均正規化害 **0.184 → 0.123**。
- 「失敗確率 × 結果」ゲートは同程度の害（**5.82%**、0.120）だが、**45% 多く**の行動を人手承認へ送る。**可逆性を考慮したルーティング**を外すと害は **15.53%** に上がり、軌道レベルのリスク予算は同一コストで害を**増やす**（**11.82%**）。
- **「これはシミュレーションだ」より強い、自身の限界文：**"Intervention effectiveness is assumed, not measured: the results rank allocation rules under the simulator's assumptions and do not establish deployment effectiveness."

移送できる主張は狭い：結果と可逆性は呼び出しごとに安く推定でき、不確実性が運ばない情報を運ぶ。だから利得はモードのメニューではなく**順位付け関数**にある。

## 5. 自己測定の負の結果

**`Donchitos/Claude-Code-Game-Studios`**（28,645★、4,017 fork、MIT、49 agents / 74 skills / 15 hooks / 14 rules / 62 templates。GitHub の*説明*は「72 workflow skills」だが README のバッジ・表・ディレクトリはいずれも **74**——分類別の算術を持つ文書は README である）は、自身の設定に対して統制比較を行い、**負の**結果を公表した：ひとつの brief から四つのゲームを作り、**ゲームコードの最初の一行より前**に書いた文書を数えた——`minimal` は **1** 本／0 分、`standard` は **30** 本／58 分。いずれも動作しテストされたゲームになったが、「二人の盲検評価者と一度の人手プレイテストが `standard` のビルドを**最下位**に置いた——余分な 29 本の文書が買ったのは追跡可能性であり、より良いゲームではない」。

引用前に境界を読む：**n=4、brief 一つ、評価者二人、プレイテスト一度**。文書量が**単調に**良いわけではない、という証拠であって、確定した順位ではない。同節の後半は前半の検査である——ゲームにとって通過するテストは十分ではなく「誰かが*見る*必要がある」——だからこのワークフローは主張するのではなくビルドを走らせる。

## 今後あらゆる「ハーネス費用」の主張で確認すること

1. **誰の分母か？** `cost_usd` 推定は請求書ではない。サブスクでは通貨はレート制限の余裕である。割合がどちらに対するものか書く。
2. **オーバーヘッドはタスクに比例するかセッションに比例するか？** **転写全体**に対するエージェント別要約はコンテキスト長で伸び、固定プロンプトは伸びない。機構がどちらかを教える。
3. **その割合は一人の一週間か、幅か？** 独立測定の幅があれば幅を引用する（18–26% → 「六分の一から四分の一」）。
4. **対抗設計は同じ予算で測られたか？** ゲートがより頻繁に承認を求めるなら「より安全」は無意味。CASEL は計算量を揃え、承認コストも併記する。
5. **失敗の単位はモデルのステップか、ハーネス自身のステップの記憶か？** ループ内に初期段階を読み直す手順があるかを問う。無ければ劣化は構造的である。
6. **プロジェクトは自分が負けた行を公表したか？** 最下位になった 30 文書ビルド、"intervention effectiveness is assumed"、遅くなった x86 セル——主張にコストを払わせる行が、残りを引用可能にする。

## 未解決の問い（アクション・アジェンダへ）

- **`agent_summary` の割合**は別アカウントや別プランで再現するか。#86879 が求める設定を Anthropic は出荷するのか（*機能要望*はロードマップではない）。
- **機能別のトークン計上**（`query_source` 型）をユーザーに晒すクライアントはあるのか、それとも OpenTelemetry だけがこの種を見られる唯一の計器なのか。
- 永続セッションに**再確認手順**（明示的な「段階 N−1 を再検証」ステップ）を足すと FeatureArc の 28.5% は動くのか、それとも劣化は手順ではなくコンテキストから来るのか。
