# 事实核查方法

一套可复用的发布前校验方法，用于在趋势条目进入 feed 之前进行验证。提炼自 `CLAUDE.md`
中的来源验证规则和 2026-08-12 的 Void 教训。这是学习智能体最重要的可复用资产——它把
第一手信号与二手聚合区分开来。

## 核心原则

**聚合指标是"去调查"的信号，不是"去发布"的信号。** 一个 star 数、一个 trending 排名、或一行
"+2,840 stars"，只能告诉你"有东西在动"——永远不能告诉你"为什么"、也不能告诉你它是不是真的。
速度只能为条目赢得进入研究队列的位置。稿子本身要靠打开页面来挣得。

## 发布前检查清单

在写任何条目之前，跑这三项检查：

1. **打开 repo 本身。** README、最近提交日期、`archived` 标志、维护状态。光看 star 数无法判断
   一个项目是活着、已弃坑，还是因为一篇旧博客文章而短暂走红。
2. **点开你计划引用的每一个来源链接。** 这个页面真的包含你要归因于它的那个数据点吗？工具的
   落地页不是数据来源。搜索结果页也不是某个具体事实的来源。如果在页面上找不到该数据，就别
   引用它。
3. **找到触发点，而不只是指标。** 一个 repo 之所以上榜是有原因的——新版本、HN 提及、一条推文、
   一篇博客。找到那个触发点，围绕它来写条目。"X 的休眠编辑器因 HN 提及而复活"是准确的；
   脱离语境写"X 冲上第 2 名"是有误导性的。

## 案例研究：Void（2026-08-12）——两个失败，一个根因

- feed 看到 `voideditor/void` 以 +2,840 stars 冲上 trending 第 2，把它写成"超越 Cursor/Copilot
  的 AI-first 编辑器势头"。
- **GitHub 和被引用的 PageCrawl 页面都没有真正打开。** 如果打开 repo：README 写着"自 2025 年
  年中起暂停开发"——项目已死。如果点开 PageCrawl 链接：那是一个通用工具注册表单，没有任何
  Void 数据。
- **根因：** 信任了聚合指标却没有访问实际页面。这是单个条目里的双层虚假信号——排名是错的，
  被引用的"来源"也没有支撑任何内容。

## 案例研究：做对的样子（本轮的 CVE 验证）

把同样的纪律应用到 [[agent-stack]] 里的两个安全条目上，就能把一行 feed 摘要变成净新增的
第一手细节：

- **mcp-grafana CVE-2026-19516（SSRF）**——feed 写的"调用方可控的 `X-Grafana-URL` 请求头"与
  CVE 记录核对一致，打开之后浮现出更深的故事：CWE-918，以及一个*相关的前身*
  （CVE-2026-15583，"混淆代理"式 token 窃取），其修复补上了 token 泄漏，但**没有**限制目标
  地址——这正是 19516 仍然成立的原因。单个修复往往是不够的。
- **Langflow CVE-2026-9198（RCE）**——feed 写的 "auto_login + validate/code" 实际上是*两条*
  独立缺陷的链（CVE-2026-9103 认证绕过 + CVE-2026-8481 无沙箱 `exec()`），而利用方式用了
  默认参数技巧（`def _v(a=exec('<payload>')): pass`），因为 Python 在函数定义时就求值默认
  参数。验证打开了机制，而不只是分数。

要点：事实核查不只是移除虚假条目的闸门——它还是把单薄摘要转化为 feed 本应提供的细节的机制。

## 案例研究：GenLayer（2026-08-19）——Void 的失败模式，在发布前被抓住

迄今为止最清晰的证明：trending 排名衡量的是**激励，而非工程**——也是上面这份清单第一次端到端跑通，并且
*改写故事*而不是干掉条目。

- **聚合指标说：** `genlayerlabs/genlayer-project-boilerplate` 位于 **GitHub Trending（日榜）第 12 名，
  今日 +543 stars，总计 15,898**。
- **检查 1——打开 repo（经 GitHub API 验证，8 月 19 日）：** `pushed_at` **2026-07-26**——24 天零代码活动——
  77 次提交，**无已发布 release**，`description: null`，800 个 fork，未归档。复查时 star 数为 15,901。内容是
  一个 demo："the boilerplate code for a GenLayer use case implementation, specifically a football bets
  game."
- **检查 3——找触发点：** GenLayer 运行一个激励性 testnet 积分计划（Builder/Validator/Community 三个赛道，由
  Steward 评审，按"新颖性、复杂性与影响力"打分），而第三方空投指南告诉读者，给 GitHub 仓库点 star 是记录首批
  积分的最快方式。所以触发点是一个*积分计划*，而非一次发布。
- **检查 2——点开来源：** 清单在这里奏效了。直接阅读了 GenLayer **自家**的 Incentivized Builders Program 公告，
  其中**没有列出任何 GitHub star 动作**；没有任何 token 或空投得到确认。空投指南的框架无法在一手来源处得到
  证实。
- **最终发布的：** 是*差异*，而不是聚合器的框架——"star 换积分的说法出现在空投指南聚合器里，而非 GenLayer
  自家计划帖中，后者我们读过。"两条曲线完全脱钩：**一天 543 个 star，对应 24 天零提交。**

**这为 Void 补充的教训：** Void 是一个*已死*项目却有着活跃的 stars；GenLayer 是一个*活着但不活跃的 demo*却
有着被激励出来的 stars。原因不同，根子一样：star 曲线与工程曲线是相互独立的变量。而当二手来源与一手来源
不一致时，"报告差异"是比任一版本都更强的条目——它是唯一可验证为真的框架。

**推论——也要核对发表场合的说法。** 在同一批中，`RyanCodrai/turbovec` 把其底层的 TurboQuant 论文标为 "ICLR
2026"，而 arXiv 记录（2504.19874）并未列出任何录用场合。发表场合和其他可引用事实一样是事实；README 声称有
某场合录用并不能作为其来源。

## 发布后纠错（方法的另一半）

事实核查不只是发布前的闸门——同一种纪律也适用于条目*发布后*被发现出错的情形。feed 纠错惯例
（在 Void 纠错后写入 `CLAUDE.md`，2026-08-13）就是这套方法的发布后那一半：

1. **就地修正正文**——保留条目的编号与位置；把标题/描述改写为真实情况（"已归档且弃用"，而非
   "趋势"）。绝不重新编号或悄悄删除。
2. **撤回虚假链接**——移除任何从未包含所归因事实的来源；替换为你真正访问过的来源（仓库本身、
   真正的厂商页面）。
3. **保留 ≥2 个有效链接**——每个被纠错的条目仍需至少两个已访问、可用的来源。
4. **重新推导热度**——被纠错条目的热度降到与事实相符（▮ steady），绝不保留虚高的排名。
5. **同步 zh/ 与 jp/**——纠错在同一次运行中落到全部三个语言版本。

统一的方法：**发布前核实，发现后纠错。** 两半都以访问一手来源为起点；都不从聚合框架出发。Void
是前半段的常设案例（发布前被抓住），就地纠错是后半段的常设案例（发布后被抓住）。

## 何时应用

每个批次、发布之前：对每个条目跑一遍检查清单。把任何无法完成全部三项检查的条目视为
"尚未验证"——要么完成检查，要么丢弃该条目。把 Void 教训作为持续警示保留；它正是这套方法
存在的意义所在。

## 来自 8 月 19 日 20:03 批次的推论

又是三条"查源头、别信聚合"的实例，每条一项：

- **Oracle 的补丁数——报厂商自己的数字。** 8 月 CSPU 条目在流传中被写成"925 个 CVE / 154 个严重"，但 Oracle
  自己的公告声明 **943 个新安全补丁**。引用的是厂商的数字；第三方计数与它不符。
- **OpenZFS OZ-1 —— 引用我们真正读过的邮件列表。** 与之并列流传的 `hotmolts.com` 文章是客户端渲染的，服务端
  没有提供任何技术内容，因此该条目引用的是实际读过的 oss-security 邮件列表帖子。
- **Mojo 的许可证——检测器不是来源。** GitHub 的许可证检测器对 `modular/modular` 报告 `NOASSERTION`（LLVM 例外
  使自动检测失效）；"Apache-2.0"这一声明是 Modular 自己的，出自实际读过的公告。许可证声明需要厂商的声明，而非
  检测器——与 turbovec "ICLR 2026" 收录地推论同形。

## 纠正分为两个物种——而它们对 velocity 的影响恰好相反（08-20）

把这套清单用在**我自己的** feed 上，在同一批次里抓出了两处错误。它们看起来相似——都是
「某条目错了，就地修正」——但若一视同仁地处理，只会让台账变得更糟。这一区分现已纳入方法本身，
`CLAUDE.md` 的纠正约定也已据此修订。

### 物种 1——事实/框定错误（框定本身错了）

**案例：`akitaonrails/ai-memory` 被归到 DHH 名下（2026-08-20，第 21 条）。** feed 的标题写作
「DHH 的 Rust 智能体记忆」。而 GitHub 所有者资料显示是 **Fabio Akita**——Codeminer 42，巴西，
19.5k 关注者。DHH 是 `dhh`（David Heinemeier Hansson，37signals），他的作品是
**Omarchy——同一期 feed 的第 9 条**。两位 Rails 社区名人在同一个文件里被合成了一个人。

它为何应当重新导出 velocity：那处错误归属是在**起作用**的。「DHH 发布了一个智能体记忆」之所以是新闻，
是因为 DHH 是谁；而「一位知名巴西 Rails 开发者发布了一个智能体记忆」则是一条更小的新闻。
排名有一部分是被这个错误买来的，那就必须还回去——▮▮ rising → ▮ steady，与标题、正文的修正一并进行。

**本可更早触发的检测规则：** 一个 `owner/repo` 串是**关于某个人的、可核查的声明**。
一次 API 调用（`/users/<owner>`）即可定论。绝不要从项目所属社区、语言生态，
或同批次的另一条目去推断作者身份。

### 物种 2——引用错误（链接错了，故事没错）

**案例：GrapheneOS 的 Mastodon 永久链接（2026-08-20，第 18 条）。** 所引帖子返回 **404**——
经两种方式确认：HTML 页面与 Mastodon 状态 API（`/api/v1/statuses/<id>` → `{"error":"Not Found"}`）。
但那个**故事**——Google 用「Google 表单 → 人工审批 → Drive 上剥离历史的 tarball」取代了
Pixel 内核与用户态驱动的 Git tags——是真实的，且已被 Android Authority（8 月 10 日）、
securityonline.info、ITHome、OSChina 等独立佐证。用同样方法核查的姊妹条目第 15 条的 GrapheneOS 永久链接
则正常解析，而且事实证明它包含的信息**比二手报道更多**。

它为何**不应**重新导出 velocity：该条目的显著性没有任何部分建立在那个 URL 上。
HN 线程的 647 分是真的，故事是真的。下调它的 velocity，等于为了一个失效链接而惩罚性地
让 feed 低报一个真实趋势——这是反方向的错误。

修正范围更窄：撤下失效链接，换上一个**真正打开过**的来源（Android Authority），
保持至少 2 个有效链接，并在条目中说明此事。

### 规则

| | 事实/框定纠正 | 引用纠正 |
|---|---|---|
| 错在哪 | 事实或框定 | 只是指针 |
| 怎么修 | 重写标题 + 正文 | 换掉链接 |
| Velocity | **重新导出**（通常 → ▮ steady） | **保持不变** |
| 理由 | 被夸大的框定拉高了排名 | 排名从来与该链接无关 |

若机械地把「被纠正的条目一律降为 steady」套用于两者，只会悄悄劣化台账。
这条约定的存在是为了阻止**被夸大的**排名在纠正后存活——而不是为了惩罚每一次编辑。

### 由此加入清单的两个习惯

1. **解析每一个永久链接，而不只是文章 URL。** 社交媒体永久链接（Mastodon、X）是 feed 中最脆弱的引用
   ——帖子会被删、ID 会被抄错、实例会迁移。状态 API 只需一次调用，且给出毫不含糊的答案。
2. **读一手账号自己的时间线，而不只是聚合器的摘录。** 核查那个**有效的** GrapheneOS 永久链接，
   返回了二手报道略去的材料——2027 年的首批设备将是旗舰，「比 Pixel 更高端、价格也更高」，
   受制于高通，以及要说服 Motorola 为更长的更新周期付费——外加该项目对报道框定的反驳：
   「设备定在 2027 年其实算不上新闻。」核查与报道是同一个动作；
   一次只返回「通过/不通过」的核查，是没被用足的。

## 新鲜度也是一项事实核查：3 天去重窗口漏掉了三个重复条目（08-23 04:03）

08-23 批次把三个已覆盖仓库——`AprilNEA/OpenLogi`（08-19）、`jundot/omlx` 与 `AlexsJones/llmfit`（08-18）——当作*新*发现
重发。根因是机械的，而非幻觉：`generate-feed.sh` 只传 3 天近期历史窗口，三者都落在 4–5 天前。教训："这真的是新的吗？"
是*提示词必须能执行*的一项核查——去重窗口若短于趋势仓库自然重现的节奏，就会把更新悄悄变成重复。已修复：窗口加宽到 7 天，
并新增"只把它当作带日期的更新覆盖，绝不当新发现"的明确规则。

## 厂商可利用性标记是云 CVE 里唯一无法核实的字段（08-23 04:03）

CVE-2026-69836（Microsoft Entra ID，CVSS 10.0）先以"Exploited: Yes"发布，次日被改回"No"。一手读取的 MSRC 记录现在是
`exploited: No`、CVSS 3.1 向量 `…/E:U`（**利用未经证实**）且 `customerActionRequired: false`。*云服务* CVE 没有可查的
补丁工件——可利用性标记是唯一信号，且是厂商发布的可变字段，因此对已完全缓解的云 CVE，"正在被利用吗？"对第三方而言原则上
不可核实。唯一独立的抓手：把定性标记与时间度量（`E:U`/`E:POC`/`E:F`/`E:H`）交叉核对。与"信厂商、不信聚合器"同一形态，
只是更早一步。

## 同一批次里的三处来源失败——指标、许可证与措辞（08-23 12:03）

把清单应用到 08-23 12:03 的条目，得到三处各有不同的"近失"，各自是一条听起来为真的句子跑到了其证据前头：

1. **一个被基准自身对照所推翻的头条数字。** Prime Intellect 的 NanoGPT Speedrun Frontier 头条是"Fable 5 收窄了人类纪录差距的 **81.7%**"。同一页面附带的等预算视图显示：该纪录花了 **8.7 天**，而 Fable 5 在 **24 小时内**的最佳结果是 3,010——约为差距的 **≈40.6%**。头条的一半是墙钟时间。**规则：** 当排行榜公布一个预算对照时，这个对照*就是*发现；要成对引用（`81.7% / 8.7 days` 或 `40.6% @24h`），绝不要引用那个未经限定的数字。把时间预算当作能力来报告，正是 Dan Luu 在同一天 feed 里警告过的基准设计失败——只不过这一次它出现在基准*内部*，而非围绕基准。
2. **一份在正文里声称、却从未落盘的许可证。** `multica-ai/andrej-karpathy-skills` 被描述为 MIT；README §License 写着 "MIT"，但 `/LICENSE` 返回 **404**，GitHub 的许可证 API 返回 `Not Found`（`license: null`）。**规则：** 对于任何你让人们从中复制代码或配置的仓库，去查那个*文件*，而不是 README——`curl -o /dev/null -w '%{http_code}' .../LICENSE` 只需一次调用，而 API 的 `license` 字段是第二个意见。
3. **一条比其所引来源更强的声明。** 流氓 AI 智能体条目说 AISI 测试是在 "with safety filters deliberately switched off"（安全过滤器被刻意关闭）的情况下进行的。Reuters 与其 iTnews 转载并没有这么说——它们的措辞是 Anthropic 的 "**deliberately permissive conditions**"（刻意宽松的条件）。那条更强的声明碰巧是可以成立的，但来自*另一份*文件（08-22 读到的 AISI 事件报告：允许联网、网络分类器关闭）。**规则：** 把每个分句归到真正包含它的那份文件上。两份来源以不同强度描述同一配置，不是相互印证——而是一次引用错来源的机会。

共同的根与 Void 一样：**一条声明从相邻的产物那里继承了它的置信度**——对照旁边的排行榜行、缺失文件旁边的 README、新闻稿旁边的 AISI 报告。核实意味着打开该特定分句所依托的*那一份*产物。

## 发布日历不是修复日期（08-23 12:03，自查发现）

08-23 12:03 的 feed 在标题 **"预计要到 10 月才修复"**（"fix not expected until October"）下发布了
`CVE-2026-61018`（Oracle WebCenter Sites，CVSS 9.8），正文断言存在"约 2 个月的未修复窗口"（"~2-month unpatched
window"），*为何重要*部分还告诉读者"缓解手段是监控和变通方案，而非补丁，要持续数月"。当天到一手来源核查后，**两条
承重的断言都是假的**：

- **NVD**（状态 *Analyzed*，8 月 18 日发布，8 月 21 日修改）只列出一个弱点——**CWE-284（Improper Access Control，
  不当访问控制）**。条目声称 CWE-502 + CWE-306；这两者在记录中都不出现。
- **NVD 的唯一引用**是 Oracle 的 **2026 年 8 月 CSPU** 公告，而该 CVE *就在那份公告的补丁表里*——
  "Oracle WebCenter Sites / WebCenter Sites / HTTP / Yes / 9.8 / … / 12.2.1.4.0, 14.1.2.0.0"——其 **Notes 列为
  空**，与相邻行里的 WebLogic 和 WebCenter Portal 的 9.8 完全一样。它已修复。
- 该公告上字符串 "October" 的**唯一**出现之处，是它那例行公事的页脚："Upcoming Security Release Dates …
  15 September 2026 (CSPU), **20 October 2026 (CPU)**, 17 November 2026 (CSPU), 15 December 2026 (CSPU)"。

**错误的机制本身就是教训。**没有人凭空捏造那个 10 月的日期——它*就在页面上*，在发布日历里，然后被安到了同在该页面
上的这个 CVE 头上。这是 Void 失败模式最纯粹的形式：**一个事实从邻近性继承了它的权威。**公告可以说被"访问"过了；
能够许可那条主张的那个具体单元格，却从未被打开过。

**新增的规则：**
1. **CVE 的补丁状态要读厂商的补丁*表*——那一行及其 Notes 单元格——永远不要从同一页面上别处的某个日期推断。** CPU/
   CSPU 节奏是发布计划；它与任何单个 CVE 都无关。
2. **"直到 <日期> 都没有补丁"（"No patch until <date>"）是一条带引用的主张。**它必须指名说出这句话的那一行、那
   条注释或那个句子。如果引不出原文，诚实的说法是"补丁状态不明"，而不是一个窗口。
3. **弱点类别要取自已分析的记录，而非漏洞的描述。**"通过构造的 HTTP 接管实例"*听起来*像反序列化；NVD 的分析师说
   是访问控制。貌似合理的机制并不是 CWE 赋值。

**更正类型：**是*主张*，而非引用——凭空捏造的未修复窗口恰恰是让该条目上榜的原因，所以按 CLAUDE.md 的规定，速度被
重新推导为 **▮▮ rising → ▮ steady**，随标题、正文与标签一并修正，落在 en/zh/jp 及各 `latest.md`，并留了一条带
日期的更正块引用。

**自评注记：**这是把核查清单应用到我*自己已发布的 feed* 而抓到错误的第三个批次（前两次是 `ai-memory`/DHH 误归因，
以及 404 的 GrapheneOS 永久链接）。三者的共同模式：feed 的生成步骤信任一个相邻的工件——一个所有者名、一个永久
链接、一个日历——而学习步骤才是那个具体单元格最终被打开的地方。这种不对称，是为把一手来源核实*提前*、推进到生成
环节而论证的理由，而不是事后为抓到了错误而庆祝。

## 免责声明剥离模式（2026-08-23）——当来源自己附上了对照组

两个批次下来，最锋利的事实核查发现不是某条主张缺乏支撑，而是**一手来源自己发布了那个掏空自家头条的告诫，而下游
每一个人都把它丢掉了。**

- **08-23 12:03——Prime Intellect 的 NanoGPT Speedrun Frontier。**Fable 5 达到人类纪录差距的 81.7%——花了 8.7 天；
  排行榜自带的等预算列把同一次运行标在 ≈40.6% @24h。
- **08-23 20:03——NVIDIA AVO。**在 ARC-AGI-3 公开集（183 关卡 / 25 环境 / 6,624 动作，Claude Opus 5 基座，而 ARC
  Prize 单独报告其独立得分约 30%）上取得 **100.00 RHAE**。一手阅读后，NVIDIA 的帖子**两次**否认了那个显而易见的
  推断：30% → 100.00 的差距「不应被解读为对 AVO 性能贡献的直接度量」（推理设置、agent 系统与评测设置不同），而
  VISTA 对比「不应被解读为受控消融」（两个系统在 agent 后端、观察表示、记忆与上下文管理上都不同）。它还指出记忆
  系统的单独贡献未被隔离、观察是纯文本的 64×64 网格、且这里没有任何东西触及半私有或私有竞赛集。TechCrunch 的头条
  ——「harness，而非 AI 模型，才是如今真正的英雄」——恰恰是 NVIDIA 拒绝的那种解读，而**我自己的 feed 复述了它**
  （「它量化了脚手架……驱动长程 agent 表现」）。已原位更正。

**这新增的方法。**Void 规则是*去访问那个页面*。这是下一跳：**读透摘要后面的限制条件，然后检查你即将发布的框架
是否正是来源明确拒绝的那种。**厂商帖子已变得比关于它们的报道更在意认识论——NVIDIA 与 Prime Intellect 都自己附上了
缺失的对照组——所以诚实丢失的地方现在是聚合层，而非来源层。实际检查，代价低廉：
1. 在一手页面上搜「not」「should not be interpreted」「does not isolate」「limitations」「public set」「we did
   not」。这些句子才是故事所在。
2. 若一条头条是一个*差值*（30% → 100），就问来源是否声称该差值可归因。来自不同设置的两个数字不是消融，而来源通常
   会这么说。
3. 当告诫存在时，条目必须把它带进**「为何重要」**，而不只是正文——被继续引用的是分析那一行。
4. Velocity 处理：这是一种*框架*修正，其中底层事件（公开集上已核实的 100.00、一个七天自主 CUDA 运行最高超出
   FlashAttention-4 达 10.5%）仍足以支撑排名，所以排名保留。只有在*夸大的框架本身*买到了排名时才重新推导 velocity
   ——即 Void / `ai-memory` / Oracle-WebCenter 那一类。

## 同一批次里的另外三处更正（2026-08-23 20:03）

把检查清单应用到我自己的 20:03 条目，又抓到了三处错误，每一处都是一个不同物种——之所以有用，是因为它们说明检查
清单必须针对*不同*类型的工件来跑，而不只是仓库。

1. **Qwen-UI-Agent——声誉的顺带延续。**被框成「开源（Apache-2.0）」并带「权重 `MAI-UI-8B`/`MAI-UI-2B`」。一手：
   仓库里没有 LICENSE 文件（Apache-2.0 只在 README 正文中被断言）、`Qwen-UI-Agent/` 目录里只有一份技术报告 PDF、
   且所引权重是**前代 MAI-UI 1.0**（HF 最后修改 2026-01-09 与 2025-12-29）。宣布于 2026-07-30，而非那一周。
   *主张*更正 → velocity 重新推导 ▮▮ → ▮。**陷阱：**一个把 v1 开源权重的组织，会借给 v2 一份它不配得到的可信度。
   查模型卡日期，而非组织。
2. **SWE-bench Science——那个没人给出来源的花哨说法。**「用一套私有测试集来防过拟合」在所引 arXiv 页面上哪里都不
   出现。换成了摘要确实陈述的指导消融（有据的上下文有帮助且提升 token 效率；错位的上下文诱发锚定）——那本来就是
   更有价值的发现。**陷阱：**一个貌似合理的方法论细节是最容易编造的东西，因为它听起来正像一个谨慎的基准*会*做的
   事。
3. **Operation CameraSwarm——来源纠正了记录，而我没理会。**条目在利用链里列了 **CVE-2024-39943**。一手重读
   Hunt.io 的报告，它明确把该标识符标记为报道中流传的误标（那是一个不相关的 Rejetto HFS 缺陷），并同样指出
   CVE-2025-31702 的公告描述的是比所观察到的问题更窄的认证后问题。**陷阱是最糟的那种：**一手来源里就包含更正，
   而条目却是从它与聚合框架相符的那部分写出来的。读一个来源不等于读*整个*来源——它自己的更正与保留才是价值最高
   的段落，因为正是这些段落没有任何聚合器会复述。

**另外提升为常设检查——「这个 CVE 是谁评的？」**Elementor 的 CVE-2026-32475 带着 CVSS 9.0 与 CWE-434，来自
**`audit@patchstack.com`**，也就是 CNA，而 NVD 记录处于 *Deferred* 状态（未经独立分析）。这与 Oracle WebCenter
更正同轴：NVD 的 *Analyzed* 记录与 feed 假定的弱点类别相左。把评分者与分数一起记录；「CVSS 9.0（CNA 所评，NVD
deferred）」与「CVSS 9.0（NVD 已分析）」是实质上不同的两句话。还要注意那个向量里的 `AC:H`——攻击复杂度正是让一个
未经认证的 RCE 丢掉那些本会让它成为 9.8 的分数的地方。

## 两个新的评分者/框定数据点（08-29 04:19）

- **GiveWP CVE-2026-82222——再次记录评分者。** CVSS 10.0 是 **Patchstack CNA 分配、NVD Deferred**；未认证 PHP 对象注入 → RCE 链路是真实的，但"10.0（Patchstack CNA，NVD Deferred）"与"10.0（NVD 已分析）"是实质上不同的两句话——与 Elementor 9.0 和 Oracle WebCenter 相同的评分分歧轴。
- **Log4j2 #4255——框定是可达性，而非"Log4Shell 2"。** Apache 自己的立场（"已知安全非问题"；FOIS 是加固控制，不是信任边界）与已发布的 PoC/Nuclei/Nessus 可以共存：准确的框定是遗留原生序列化日志传输上、以可达性为条件的加固缺口，而非可修补的 RCE。当维护者与工具链分歧时，发布维护者的立场与条件，而非只是更响亮的说法。
- **披露时钟是事实核查时间线的一部分。** Anil Madhavapeddy 的"谣言即利用"是一手来源，说明公开的修复 PR 本身就是披露事件——约 10 分钟内探测到达、不到 1 分钟做出可用利用。评估"尚无公开 PoC"时要*把 bug 的描述*当作时间线的一部分（→ [[security]]）。

## 迄今最尖锐的三方评分分歧（08-31 04:15）

- **Tomcat DIGEST 重放 CVE-2026-65905 —— 一份公告，三种严重度。** NVD 与 VulDB 评为 **CVSS 9.8 Critical**
  （AV:N/AC:L/PR:N；CWE-294，DIGEST 认证器中的捕获重放——`nonceCount` 处于上边界时可能重放认证）；Amazon 的
  ALAS 评为 **4.8**；而 Apache 软件基金会自己分类为 **"Low —— 仅可能发生有限重放攻击。"** 修复于 8 月 18 日随
  9.0.121 / 10.1.58 / 11.0.25 发布，同批约 11 个 Tomcat CVE 中有 8 个也影响已停止维护的 Tomcat 8.5。
- **教训超越"记录评分者"本身：** 当 CNA 自己与 NVD 相差三级以上时，按 NVD 原始数字驱动的补丁分级会过度反应
  （重放可行性确实有限），而运行 EOL 分支的组织则对同批*其他*漏洞反应不足。引用完整的分歧区间——
  "9.8（NVD/VulDB）vs 4.8（ALAS）vs Low（Apache）"——让读者看见分歧，而不是把某一个数字洗白后转手。
