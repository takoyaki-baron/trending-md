# 框架开销——框架在没有账单条目的情况下花掉的两项资源

一个框架为用户要求它做的工作计费，同时隐性支付另外两件事：**花在描述自己上的 token**，与**花在复查自己已做过的事上的注意力**。两者都不出现在用户发出的请求里，都随会话规模而非随任务规模增长，而 2026-10-29 20:00 批次把两者各测了一次——一个量化成账单占比，一个量化成一个缺陷之后的失败率。

相邻文件：[[harness-reliability]]（同一个接缝在故障注入、StateMirror、HarnessMM 下的测量）、[[token-economics]]（成本边界；缓存读取占 agent 化支出的 96–99%）、[[agent-stack]]（作为产品类别的 harness）、[[fact-check]]（如何读一张自报的表）、[[frontier-models]]（作为基准列的 harness）。

**主张：**框架自己的簿记与任务争夺同样的两项资源，而每一项的有用单位是**正在被花掉的那件事的占比**——支出的 16.4%、漏检缺陷的 95%——不是每次调用的成本。一个按**后果**（而非按置信度）定价的策略、以及**分层**（而非整块）揭示记忆的设计，是当前对两者的最佳答案。

## 1. token 开销：一条状态行花掉六分之一的账单

**Claude Code 的 `agent_summary`**（flamerix.ai 测量，2026-10-29）。每隔约 30 秒，对**每一个后台 agent**，客户端把该 agent 的**完整转录**发给它自己的模型，要求「用 **3–5 个词**描述你最近一次动作」；答案只更新 agent 面板里的一行状态，从不进入模型或对话。自 **2.1.232**（2026 年 8 月）起默认开启，"**没有任何设置能关掉它**"——所链接的 issue 正是一个要求提供该设置的*功能请求*（[anthropics/claude-code#86879](https://github.com/anthropics/claude-code/issues/86879)，2026-08-15 提交，仍未关闭）。

测量来自客户端自己的 **OpenTelemetry** 导出，按 `query_source` 分组：

| 指标 | `query_source = agent_summary` | 主对话 |
|---|---|---|
| 占 Claude Code 全部支出（`cost_usd`） | **16.4%** | 15.7% |
| 占全部 API 请求 | **19.7%** | — |
| 这部分支出落在 Opus 上的比例 | **96%** | — |

输入/输出比约 **9,000 : 1**——一个摘要器读完整份转录只为写三个词，所以成本与**上下文长度**成正比，这正是该比值是机制而不是细节的原因。该 issue 线程收录了**四项独立测量，区间 18–26%**，所以可辩护的说法是「**六分之一到四分之一**」，而不是「16.4%」。

**单位，也是这个断言通常断裂的地方：**16.4% 是 Claude Code **自己的 `cost_usd` 估算**的占比，不是发票的占比。在订阅制下损失的是**速率上限余量**，不是钱——来源自己写了这一句（"if you are on a subscription, what you lose is rate-limit headroom"），而摘要式报道通常会丢掉它。

**这套测量手法可推广到这个客户端之外。**钩子是一段约 80 行的 **Bun 预加载**（`BUN_OPTIONS=--preload`），它包装 `setTimeout`/`setInterval`，当回调的源码文本匹配某个摘要器锚点时返回一个惰性句柄。它在模块以**预编译 Bun 字节码**发布的情况下仍然有效——因为即便从字节码执行，`Function.prototype.toString` 仍返回回调的**源码文本**，于是这个定时器可以靠其内部的*字符串*而非身份被识别。任何打包运行时都有这一性质，且是双向的：它既是你找到未文档化定时器的方法，也是匹配脆弱的原因。

**来源公布了自己的 fail-open 清单**（这是它可被引用的原因）：日志行或 query-source id 被改名；回调经 `fn.bind(...)` 传入（`toString` 里没有源码）；锚点字符串移到回调外的共享常量；或定时器改用未包装的 API（`timers/promises`、调度循环）。其 **Tested versions** 表覆盖 2.1.257 → 2.1.312，对一次约 2.5 分钟的 agent 运行统计 summary fork 次数，无钩子／钩子通过／钩子关闭分别为 **5 / 5 / 0**——即钩子是靠*数它阻止了多少次 fork* 来验证的，而不是靠断言它装上了。

## 2. 反向设计：分层揭示记忆

**`thedotmack/claude-mem`**（104,222★、9,193 fork、Apache-2.0，创建于 2025-08-31、最后推送 2026-10-29——一个一年多的项目，一手核实）从存储端回答同一个成本问题。它的检索**不是**「嵌入并返回」：三层 MCP 工具——

1. `search` → 带 ID 的紧凑索引（**约 50–100 token/条**），
2. `timeline` → 围绕幸存条目的时间线上下文，
3. `get_observations` → **只对被筛选出的 ID** 取完整细节（**约 500–1,000 token/条**）。

agent 记忆库的失效模式不是召回，而是**上下文成本**，所以两遍过滤把昂贵的 token 只花在模型已经选中的行上。两条要与之保持距离的说法：README 里的「**约 10× token 节省**」背后没有基准章节（引用时须写明是项目自报），而那两个 token 区间是**估计值**，不是测量值。

两个会咬人的安装细节：`npm install -g claude-mem` 只安装「**SDK/库**——不注册插件钩子、也不会搭建 worker 服务」（全局安装看起来成功却什么都没交付）；对某个受支持的主机，默认是 **CMEM Pro**（托管记忆），本地观察器需要显式 opt-in（`--provider host`）——把「持久上下文」和「发送到某项服务」这两句话放在一起读，再决定是否指向专有仓库。

## 3. 注意力开销：没人重读的那个缺陷

**FeatureArc**（arXiv 2610.37434，2026-10-27 提交；**腾讯混元团队** + 香港中文大学——单位读自 HTML 全文，而非摘要页）评估的是「在 agent 自己先前工作**之后**到来」的请求：**10 个编码 agent**、**73** 个人工复核任务、每任务 **2–10 个阶段**，单一持久会话与工作区，**没有外部测试反馈、没有回滚**。

| 测量 | 数值 |
|---|---|
| 第一阶段汇总成功率 | **62.7%** |
| 整个特性在最终代码上测试时的汇总成功率 | **28.5%** |
| 失败的后段阶段中含**继承缺陷**的比例 | **72.9%** |
| 失败之后的阶段中，先前错误仍**未被注意**的比例 | **约 95%** |

这个 95% 把失效从能力搬到了**注意力**：处于第 4 阶段的 agent 并不是在第 4 阶段的请求上失败，而是在一个它没有程序去复查的地基上正确地施工，而它的自测很少回头看早期阶段。这是关于**这些系统如何接线**的陈述——只追加的历史、只覆盖当前步骤的测试——而不是关于模型质量；正是无回滚的设计拿掉了那个会说「等等，周二的缓存失效是错的」的人。

两点可信度说明：该流水线是厂商**自己**的评测装置（它「把内部评测扩展到这一设定，并指导 Hunyuan 的研发」），所以按自测来读那张逐 agent 表；73 个任务、阶段取自真实历史，规模很小——足以说「顺序特性开发在这个 harness 里会衰减」，不足以给这 10 个 agent 排名。

## 4. 按后果、而不是按置信度定价的控制

**CASEL**（arXiv 2610.36570，2026-10-27 提交）用一个逐调用的选择替代不确定性阈值，在六种模式中择一——直接执行、验证、沙箱、澄清、审批、弃权——最小化由校准失败概率、**依赖状态的后果、可逆性、歧义、证据新鲜度**构成的**每种模式的成本**。

- 受控仿真，**20 个种子 × 每个 120,000 次测试动作**，"every method has the same intervention menu and **the same compute cost**"——对照组是按不确定性排序的门控。
- 有害副作用轨迹 **14.75% → 7.02%**；平均归一化伤害 **0.184 → 0.123**。
- 「失败概率 × 后果」门控达到相近伤害（**5.82%**、0.120），但把 **45% 更多**的动作送去人工审批；去掉**可逆性感知路由**后伤害升至 **15.53%**；轨迹级风险预算在同一成本下**反而升高**伤害（**11.82%**）。
- **它自己的限制句，比「这只是仿真」更强：**"Intervention effectiveness is assumed, not measured: the results rank allocation rules under the simulator's assumptions and do not establish deployment effectiveness."

可迁移的断言很窄：后果与可逆性在每次调用上都便宜地可估，且携带不确定性不携带的信息，所以增益在**排序函数**上，而不在模式菜单上。

## 5. 自我测量的负面结果

**`Donchitos/Claude-Code-Game-Studios`**（28,645★、4,017 fork、MIT、49 agents / 74 skills / 15 hooks / 14 rules / 62 templates；GitHub *描述*写「72 workflow skills」，而 README 的徽章、表格与目录都写 **74**——README 是那个带分类算术的文档）对自己的配置跑了一次受控比较，并公布了**负面**结果：同一份 brief 做出四个游戏，统计**第一行游戏代码之前**写了多少文档——`minimal` **1** 份／0 分钟，`standard` **30** 份／58 分钟——四个都能运行且有测试，而「两位盲评者加一次人工试玩把 `standard` 版本排**最后**——多出来的 29 份文档买到的是可追溯性，不是更好的游戏。」

引用前先读边界：**n=4、一份 brief、两位评审、一次试玩**。它是「文档级别**并非**单调有益」的证据，不是一个可以当作定论的排名。同一节的另一半是对前半段的检查——对游戏而言通过的测试并不足够，「得有人*看*它」——这正是该工作流去跑构建而不是断言构建的原因。

## 未来任何「harness 成本」断言该查什么

1. **谁的分母？** `cost_usd` 估算是估算不是发票；订阅下货币是速率上限余量。写清那个百分比是哪一种。
2. **开销是随任务增长还是随会话增长？** 对**完整转录**做逐 agent 摘要会随上下文长度增长；固定提示不会。机制会告诉你属于哪种。
3. **这个占比是一位订阅者的一周还是一个区间？** 来源给出独立测量的区间时引用区间（18–26% → 「六分之一到四分之一」）。
4. **反向设计是在同一预算下测的吗？** 如果门控更频繁地请求审批，「更安全」就没有意义；CASEL 拉平算力，并把审批成本也一并报出。
5. **失效的单位是模型的步骤，还是 harness 对自己步骤的记忆？** 问循环里有没有任何程序会重读早期阶段；如果没有，衰减就是结构性的。
6. **项目公布了自己输的那一行吗？** 排最后的 30 文档构建、"intervention effectiveness is assumed"、变慢的 x86 单元格——让论断付出代价的那一行，才使其余部分可被引用。
