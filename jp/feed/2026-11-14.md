## 5. 「システムプログラミングで C より Zig を選ぶ理由」——errdefer が goto の階段を置き換え、C が残すものにも正直

- **Velocity:** ▮▮ rising
- **Source:** mtsoukalos.eu · 196+ pts on HN · 6.7h ago (~22:00 UTC+8)
- **Tags:** `zig` `c` `systems-programming`

Mihalis Tsoukalos——以前の「なぜ Rust ではなく Zig か」に続いて——より難しい比較に挑む。Zig と C は同じものを求めているからだ：小さな言語、GC なし、マシンに近い。論文の中心はリソースクリーンアップの階段だ。Linux カーネル流の `goto fail; fail_name: …` の滝——解放が割り当てから遠く、ラベルの順序を手で維持する——対 Zig の `errdefer`、解放を割り当てのすぐ隣に置き、自動で逆順に巻き戻す。全サンプルは Mac 上で **Zig 0.17 と clang** でコンパイルした。構えは意図的に改宗の檄文ではない：「C is my favorite programming language! I am writing it because I do not want to write new code in C any more」——C の強み（一冊で収まる小ささ、1990 年代のコードが今日もコンパイルできること、あらゆる CPU 用のコンパイラ）は先に敬意を払う。

**Why it matters:** Zig vs Rust の議論が注目を独占するが、C から Zig への移行のほうが実務的な対象ははるかに大きい——そして本稿は「儀式なしのクリーンアップ」という Zig の論拠が最も単純な一軸をきれいに論証する。「なぜ Rust ではなく Zig」に続く「なぜ C ではなく Zig」は、実際のプログラマがどう言語を選ぶか——一度に一つの痛みだけ——を見せる窓でもある。

> "C is my favorite programming language! I am writing it because I do not want to write new code in C any more."

## 10. LeWM で 600 実験の果てに：JEPA の予測は最初からボトルネックではなかった——計画のほうだった

- **Velocity:** ▮▮ rising
- **Source:** haddyalchaer.com · 119+ pts on HN · 2.8h ago (~01:55 UTC+8)
- **Tags:** `jepa` `world-models` `research`

Yann LeCun チームの JEPA ワールドモデル **LeWM**（ベンチマークは Push-T）への数か月に及ぶ独立再現研究が 600 実験を報告し、ヘッドラインの結果は居心地が悪い：学習済み予測器をシミュレータの**完全な物理**に差し替えても成功率はほとんど動かない。250 の長視界タスクで **78% → 77%**。予測はとっくに十分だった。足りなかったのは計画だ。リリース物をそのまま使うと LeWM は 75 ステップ視界のタスクを **22%** しか解けないが、著者の訓練不要の計画手法 4 種で **85%** まで伸びる。理想的なエキスパートのサブゴールを渡されたプランナーにほぼ匹敵する。サブゴール間隔が大半を説明する（LeWM は 25 ステップまでは正確——完全物理の 90.5% に対し 89.7%——で、75 で劣化する）。そしてゴールの採点方法を一箇所だけ変えるだけで **60 ポイント**加わる。完全物理がもたらした利益の 3 倍だ。

**Why it matters:** JEPA 対 生成型の論争は、モデルが何を予測すべきかを主に論じる。この実験が言うのは、分散が大きいのは予測の**使い方**のほうだということだ——サブゴール構造とゴールスコアリングの効きは、予測の忠実度を大きく上回った。方法論的には：著者一人、ベンチマーク一つ、コード公開の主張なし——有力な現場報告として読むべきで、確定した結果ではない。
