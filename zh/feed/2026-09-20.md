## 4. PlanetScale 发布 Tin——BM25 全文搜索成为 Postgres 原生索引类型，但闭源

- **Velocity:** ▮▮ rising
- **Source:** Hacker News · 139+ pts · 61 comments · ~14h ago (~21:52 UTC+8)
- **Tags:** `postgres` `search` `bm25` `full-text-search` `database`

Tin（"Text INdex"）是一种新的 Postgres 索引类型——`CREATE INDEX … USING tin(col)` 配
`==>` 操作符——支持 BM25 top-k、布尔/短语/跨度匹配以及模糊/通配符/正则搜索。设计巧点：
直接用 Postgres 原生的 48 位 `ctid` 作文档 ID（无需 ID 映射表），再把页号+偏移编码为两级
位图，使合取变成向量化 AND/OR，计数用 POPCNT。PlanetScale 宣称在 85 GB/1.5 亿文档语料上
吞吐量达到竞品的 8 倍以上。9 月 16 日 GA，随 PlanetScale 托管 Postgres 提供。

**Why it matters:** 看基准表之前先看注意事项：索引是闭源的（唯一的公开仓库
`planetscale/lead` 明确标注"非生产用途"，Tin 开发者还在帖子里为专有模式辩护）；基准查询
是合成的；索引体积约为语料的 60%；一个竞品无法跑完全部负载，相应的数字直接排除了它。
作者自己也承认结果"可能难以相信"。即便如此，一家主流 Postgres 托管商从零自研搜索引擎，
说明集成 BM25 正在成为标配——而 Tin 也是"开放 Postgres 之上的专有扩展"这一路线最尖锐的
新试金石。

## 11. 只报采样数 N 不够——决定测试时扩展能耗的是生成调度方式，而不是 N

- **Velocity:** ▮ steady
- **Source:** Hugging Face Papers · 16 upvotes · arXiv Sep 16
- **Tags:** `test-time-compute` `efficiency` `measurement` `inference`

一项两人系统研究显示，同样的候选预算 N，成本因调度方式而天差地别。在 500 条 GSM8K 提示上
把 N 从 1 提到 8，Phi-3-mini 准确率 +8.4 分、Qwen2.5-1.5B +18.4 分——但在固定 N=8 时，
八次串行调用（8×1）的 GPU 设备总能耗是一次批处理调用（1×8）的 4.64–4.86 倍，P95 延迟为
其 5.77–6.12 倍（A100）。该模式在三个 A100 节点以及 SciQ/V100 上均复现。

**Why it matters:** 这是对"只报 N"的测试时扩展论文的直接方法论挑战：评测应当在准确率之外
同时公布调度方式和 GPU 级指标，否则效率声明之间不可比。论文把结论限定在"候选彼此独立
且显存允许"的前提下，范围是两个小模型、两个数据集——没有前沿规模验证。它是测量，不是
新方法。

- **Tags:** `cve` `elixir` `http` `request-smuggling`

`Mint.HTTP1.Parse.chunk_size/1` 在第一个非十六进制字节处停止并原样返回剩余部分，因此

**Why it matters:** Mint 是 Phoenix/Elixir 生态默认 HTTP 客户端的底层依赖，属于本周就该
钉死版本的供应链级修复。公告对可利用边界写得很清楚——客户端与受攻击者影响的源站之间
必须存在一个 RFC 严格的代理/负载均衡/WAF 且复用 HTTP/1 连接——直连源站的客户端不受影响。
请求走私这一类问题进入 BEAM 客户端，才是值得记录的趋势。
